Orchestration — Docker Swarm — 25%

Swarm

Architecture Swarm

Manager Nodes

Maintiennent l'état du cluster (Raft consensus). Reçoivent les commandes docker service. Peuvent aussi exécuter des tasks (par défaut). Recommandé : 3 ou 5 managers pour la HA.

Worker Nodes

Exécutent les containers (tasks). Ne participent pas aux décisions Raft. Peuvent être promus managers avec docker node promote.

Quorum Raft

Nombre de managers requis pour maintenir le quorum : (N/2)+1. 3 managers → 2 requis. 5 managers → 3 requis. Sans quorum, le cluster est en lecture seule.

Services vs Tasks

Service : définition déclarative (image, replicas, ports, contraintes). Task : unité d'exécution = 1 container sur 1 nœud. 1 service → N tasks.

Service Modes

Replicated (défaut)

Nombre exact de réplicas distribués sur les nœuds. --replicas N. Swarm décide de la distribution. Peut avoir plusieurs tasks sur le même nœud.

Global

Une task par nœud, automatiquement. Idéal pour les agents de monitoring, log collectors. --mode global. Pas de --replicas avec global.

Update Policy

  • --update-parallelism : tasks mises à jour en parallèle
  • --update-delay : pause entre les batchs
  • --update-failure-action : pause/continue/rollback

Rollback

  • docker service rollback SERVICE
  • --rollback-parallelism
  • --rollback-delay
  • Historique : 2 versions max par défaut
# Initialiser un Swarm
docker swarm init --advertise-addr 192.168.1.10

# Rejoindre le Swarm (affiche le token)
docker swarm join-token worker
docker swarm join-token manager

# Nœuds
docker node ls
docker node inspect NODE_ID
docker node update --availability drain NODE_ID  # vider un nœud
docker node promote NODE_ID
docker node demote  NODE_ID

# Créer un service
docker service create \
  --name web \
  --replicas 3 \
  --publish 80:80 \
  --network overlay-net \
  --update-parallelism 1 \
  --update-delay 10s \
  nginx:alpine

# Mettre à jour un service
docker service update --image nginx:1.25 web
docker service scale  web=5

# Inspecter
docker service ls
docker service ps  web         # liste des tasks
docker service logs web

# Stack (Compose pour Swarm)
docker stack deploy -c docker-compose.yml mystack
docker stack ls
docker stack services mystack
docker stack rm      mystack

docker service create \

# Ajouter un label à un nœud
docker node update --label-add env=prod NODE_ID

  nginx

Secrets & Configs Swarm

Secrets

Données sensibles chiffrées au repos et en transit (TLS mutual). Montés en /run/secrets/NOM. Accessibles uniquement aux containers du service qui y ont accès.

echo "mypass" | docker secret create db_pass -
docker service create \
  --secret db_pass \
  myapp

Configs

Similaires aux secrets mais non chiffrés. Pour les fichiers de configuration (nginx.conf, etc.). Montés à l'emplacement choisi dans le container.

docker config create nginx_conf nginx.conf
docker service create \
  --config source=nginx_conf,target=/etc/nginx/nginx.conf \
  nginx

Images & Registry — 20%

Images

Dockerfile — instructions clés

# Dockerfile de référence
FROM        node:20-alpine AS builder     # Multi-stage build
WORKDIR     /app
COPY        package*.json ./
RUN         npm ci --only=production       # layer cache optimisé
COPY        . .
RUN         npm run build

FROM        node:20-alpine                 # image finale plus légère
WORKDIR     /app
COPY        --from=builder /app/dist ./dist
COPY        --from=builder /app/node_modules ./node_modules

EXPOSE      3000
ENV         NODE_ENV=production
ARG         VERSION=latest                 # disponible uniquement au build
LABEL       maintainer="team@example.com" \
            version="${VERSION}"

USER        node                           # ne pas rester root !
HEALTHCHECK --interval=30s --timeout=3s \
            CMD curl -f http://localhost:3000/health || exit 1
ENTRYPOINT  ["node"]                       # forme exec (préférée)
CMD         ["dist/server.js"]             # arguments par défaut

Build & Registry

# Build
docker build -t myapp:1.0 .
docker build -t myapp:1.0 --no-cache .
docker build --build-arg VERSION=1.2 -t myapp:1.2 .
docker build --target builder -t myapp:builder .  # multi-stage partiel

# Tag & push
docker tag  myapp:1.0 registry.example.com/myapp:1.0
docker push registry.example.com/myapp:1.0
docker pull registry.example.com/myapp:1.0

# Registry privé local
docker run -d -p 5000:5000 --name registry registry:2

# Authentification
docker login  registry.example.com
docker logout registry.example.com

# Inspecter une image
docker inspect   myapp:1.0
docker history   myapp:1.0        # layers et leurs tailles
docker image ls  --filter dangling=true  # images "dangling" (sans tag)

# Nettoyage
docker image prune               # supprime les dangling
docker system prune -a           # tout nettoyer (containers, images, volumes)

# Save/load (sans registry)
docker save  myapp:1.0 | gzip > myapp.tar.gz
docker load  < myapp.tar.gz

# Export/import (container → image, perd l'historique)
docker export CONTAINER_ID | gzip > container.tar.gz
docker import container.tar.gz myapp:imported
✓ Multi-stage builds Réduit drastiquement la taille des images finales en séparant les outils de build (compilateurs, dépendances de dev) de l'image de production. L'image finale ne contient que le strict nécessaire.

Layers & Cache

Union Filesystem

Les images sont des stacks de layers en lecture seule. Le container ajoute un layer R/W au-dessus. OverlayFS est le driver par défaut sur Linux.

Optimiser le cache

Placer les instructions qui changent rarement en premier (FROM, RUN apt-get). Copier les fichiers de dépendances avant le code source pour profiter du cache npm/pip.

Réduire la taille

  • Utiliser des images Alpine
  • Multi-stage builds
  • Nettoyer dans le même RUN : apt-get clean && rm -rf /var/lib/apt/lists/*
  • Fichier .dockerignore

Content Trust (DCT)

Docker Content Trust avec Notary : signe et vérifie les images. DOCKER_CONTENT_TRUST=1 force la vérification des signatures avant pull/run.

Networking — 15%

Réseau

Drivers réseau

bridge (défaut)

Réseau isolé sur un seul hôte. Les containers sur le même bridge se parlent par nom (DNS Docker interne). La bridge par défaut (docker0) ne supporte pas le DNS par nom — créer une bridge custom.

overlay

Réseau multi-hôtes pour Docker Swarm. Chiffrement optionnel (--opt encrypted). Utilise VXLAN pour encapsuler les paquets. Requis pour les services Swarm inter-nœuds.

host

Le container partage le namespace réseau de l'hôte. Pas d'isolation réseau. Performances maximales. Linux uniquement. Pas de -p nécessaire.

macvlan

Assigne une adresse MAC physique à un container. Le container apparaît comme un device physique sur le réseau. Utile pour les applications legacy qui nécessitent une IP sur le réseau physique.

ipvlan

Similaire à macvlan mais partage l'adresse MAC de l'interface parent. Mode L2 (switch) ou L3 (routeur). Contourne les limitations MAC sur les switchs managés.

none

Pas de réseau. Container totalement isolé. Utile pour les jobs batch qui n'ont pas besoin du réseau.

# Réseau bridge custom (DNS par nom activé)
docker network create --driver bridge \
  --subnet  172.20.0.0/16 \
  --gateway 172.20.0.1 \
  my-network

# Réseau overlay (Swarm)
docker network create --driver overlay \
  --attachable \          # permet aux containers standalone de s'attacher
  --opt encrypted \     # chiffrement data-plane
  my-overlay

# Inspecter
docker network ls
docker network inspect my-network
docker network connect    my-network CONTAINER   # connecter à chaud
docker network disconnect my-network CONTAINER

# Publication de ports
docker run -p 8080:80           # host:container
docker run -p 127.0.0.1:8080:80 # bind sur une IP spécifique
docker run -P                   # publie tous les EXPOSE sur ports aléatoires

Security — 15%

Sécurité

Namespaces Linux

Isolation des containers via les namespaces kernel : PID, NET, MNT, UTS, IPC, USER. Chaque container a ses propres namespaces isolés.

cgroups

Control Groups limitent les ressources : CPU, mémoire, I/O, réseau, PIDs. Empêchent qu'un container monopolise les ressources de l'hôte (fork bomb, etc.).

Seccomp

Secure Computing Mode : filtre les appels système. Docker applique un profil seccomp par défaut qui bloque ~44 syscalls dangereux. Profil custom avec --security-opt seccomp=profile.json.

AppArmor / SELinux

AppArmor (Ubuntu/Debian) et SELinux (RHEL/CentOS) : MAC (Mandatory Access Control). Docker applique un profil AppArmor par défaut. --security-opt apparmor=PROFILE.

Capabilities Linux

Docker retire la plupart des capabilities root. --cap-drop ALL + --cap-add uniquement ce qui est nécessaire. --privileged à éviter absolument en production.

Rootless Docker

Docker daemon et containers s'exécutent sans privilèges root. Réduit la surface d'attaque. Limitations : certains drivers réseau/stockage non disponibles. Activé avec dockerd-rootless.sh.

# Sécuriser un container
docker run \
  --read-only \                   # filesystem en lecture seule
  --tmpfs /tmp \                  # tmpfs pour les écritures temporaires
  --cap-drop ALL \                # supprimer toutes les capabilities
  --cap-add  NET_BIND_SERVICE \   # rajouter uniquement ce qui est nécessaire
  --security-opt no-new-privileges \  # empêche l'escalade de privilèges
  --user     1000:1000 \          # utilisateur non-root
  --pids-limit 50 \               # limite fork bomb
  nginx

# Vérifier les capabilities
docker inspect CONTAINER | grep -A5 CapAdd

# Scan de vulnérabilités (Docker Scout)
docker scout cves myimage:latest
docker scout quickview myimage:latest
⚠ Montage du socket Docker Monter /var/run/docker.sock dans un container donne un accès root effectif à l'hôte. À éviter absolument en production. Si nécessaire, utiliser un proxy autorisant uniquement les opérations requises.
✓ Docker Content Trust (DCT) export DOCKER_CONTENT_TRUST=1 force la vérification des signatures Notary avant tout push/pull. Garantit l'intégrité et l'authenticité des images. Clés gérées par docker trust.

Storage & Volumes — 10%

Storage

Volumes (recommandés)

Gérés par Docker dans /var/lib/docker/volumes/. Indépendants du cycle de vie du container. Partageables entre containers. Supportent les drivers de volume (NFS, AWS EFS, etc.).

Bind Mounts

Monte un chemin absolu de l'hôte dans le container. Utile en développement pour le live reload. Dépendant de la structure de l'hôte. Moins portables que les volumes.

tmpfs Mounts

Stockage en mémoire RAM. Données perdues à l'arrêt du container. Utile pour les données sensibles temporaires (tokens, caches) qui ne doivent pas persister sur disque.

Volume Drivers

  • local (défaut)
  • nfs — NFS v3/v4
  • rexray — multi-cloud (EBS, EFS…)
  • vieux/sshfs — SSHFS
  • Plugins cloud natifs (AWS, Azure, GCP)
# Volumes
docker volume create my-vol
docker volume ls
docker volume inspect my-vol
docker volume rm      my-vol
docker volume prune              # supprime les volumes non utilisés

# Monter un volume
docker run -v      my-vol:/data nginx          # syntaxe courte
docker run --mount type=volume,src=my-vol,dst=/data nginx # syntaxe longue

# Bind mount
docker run -v      /host/path:/container/path nginx
docker run --mount type=bind,src=/host/path,dst=/container/path,readonly nginx

# tmpfs
docker run --tmpfs /tmp:size=100m,mode=1777 nginx
docker run --mount type=tmpfs,dst=/tmp,tmpfs-size=100m nginx

# Volume NFS (driver local avec opts)
docker volume create --driver local \
  --opt type=nfs \
  --opt o=addr=nfs-server.example.com,rw \
  --opt device=:/exports/data \
  nfs-vol

# Volume dans Swarm (service)
docker service create \
  --mount type=volume,src=my-vol,dst=/data \
  nginx

Pièges & erreurs fréquentes

Exam

🚫 CMD vs ENTRYPOINT

CMD est remplacé par les arguments de docker run. ENTRYPOINT reste fixe (sauf --entrypoint). Pour une image avec un binaire fixe, utiliser ENTRYPOINT + CMD pour les args par défaut.

🚫 EXPOSE ne publie pas le port

EXPOSE est documentation uniquement. Il faut -p host:container ou -P pour publier réellement. Sans publication, le port n'est accessible qu'entre containers sur le même réseau.

🚫 Bridge default vs custom

Le réseau bridge par défaut (docker0) ne supporte pas la résolution DNS par nom. Créer un réseau bridge personnalisé active automatiquement le DNS par nom de container.

🚫 Nombre de managers Swarm

Toujours impair : 3 ou 5. Avec 2 managers, perte d'un manager = pas de quorum. Avec 4 managers, même tolérance que 3. Maximum recommandé : 7 managers.

🚫 docker commit en production

docker commit crée une image depuis un container modifié mais sans Dockerfile reproductible. Résultat opaque, non versionnable. À éviter en production — toujours reconstruire depuis un Dockerfile.

🚫 Layers et secrets dans les images

Un RUN apt-get install SECRET suivi de RUN rm SECRET ne supprime pas le secret de l'image — il reste dans le layer précédent. Utiliser --secret avec BuildKit ou des multi-stage builds.

🚫 docker service vs docker run

docker run ne fonctionne que localement. docker service create est la commande Swarm. Les services sont gérés par Swarm et redémarrés automatiquement. docker run ne gère pas la haute disponibilité.

🚫 --mode global vs replicated

En mode global, --replicas n'est pas accepté. 1 task par nœud automatiquement. En mode replicated, --replicas est requis (défaut : 1).

🚫 Volumes vs Bind mounts

Avec un bind mount, si le chemin hôte n'existe pas, Docker le crée comme répertoire. Avec un volume nommé, Docker initialise le volume avec le contenu de l'image (si le répertoire existe). Comportement différent !

🚫 --privileged en production

--privileged désactive toute isolation de sécurité (seccomp, AppArmor, capabilities). Équivaut à donner un accès root complet à l'hôte. Jamais en production — utiliser des capabilities spécifiques à la place.
