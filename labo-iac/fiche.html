3Parcours A : créer 3 VM Linux avec TerraformParcours A
Terraformcloud-initfor_each
# terraform/linux.tf : 3 VM clonées depuis les modèles cloud-init locals { linux = { lin-01 = { tpl = 9000, ip = "10.0.0.61/24" } lin-02 = { tpl = 9001, ip = "10.0.0.62/24" } lin-03 = { tpl = 9000, ip = "10.0.0.63/24" } } } resource "proxmox_virtual_environment_vm" "linux" { for_each = local.linux name = each.key node_name = "pve1" tags = ["terraform", "lab", "linux"] clone { vm_id = each.value.tpl } agent { enabled = true } cpu { cores = 2 } memory { dedicated = 2048 } network_device { bridge = "vmbr0" } initialization { ip_config { ipv4 { address = each.value.ip gateway = "10.0.0.1" } } user_account { username = "ops" keys = [var.ssh_public_key] } } }
cd terraform export TF_VAR_pve_endpoint=https://pve1.lab.local:8006/ export TF_VAR_pve_api_token='terraform@pve!tf=SECRET' terraform init && terraform plan && terraform apply ssh ops@10.0.0.61 'hostnamectl' # vérifier la connexion par clé
Prends le réflexe plan → lecture → apply. Pour repartir de zéro : terraform destroy (uniquement dans ce labo).

5Parcours B : créer les VM du cluster RKE2Parcours B
TerraformCloud-initIP fixes
# terraform/rke2.tf : 3 serveurs + 1 worker locals { rke2 = { rke2-s1 = { ip = "10.0.0.51/24" } rke2-s2 = { ip = "10.0.0.52/24" } rke2-s3 = { ip = "10.0.0.53/24" } rke2-w1 = { ip = "10.0.0.54/24" } } } resource "proxmox_virtual_environment_vm" "rke2" { for_each = local.rke2 name = each.key node_name = "pve1" tags = ["terraform", "lab", "rke2"] clone { vm_id = 9000 } agent { enabled = true } cpu { cores = 4 } memory { dedicated = 8192 } disk { datastore_id = "local-lvm" interface = "scsi0" size = 40 discard = "on" iothread = true } network_device { bridge = "vmbr0" } initialization { ip_config { ipv4 { address = each.value.ip gateway = "10.0.0.1" } } dns { servers = ["10.0.0.1"] } user_account { username = "ops" keys = [var.ssh_public_key] } } } output "rke2_ips" { value = { for k, v in local.rke2 : k => v.ip } }
  • Pour tester la redondance, répartis les VM sur plusieurs nœuds Proxmox (node_name) si tu as un cluster : sinon un seul nœud Proxmox est un point de défaillance commun
  • Vérifie que rke2-s1..s3 et l'IP virtuelle 10.0.0.50 sont hors de la plage DHCP
  • Les disques SSD comptent : la latence disque est la première cause d'instabilité d'etcd
6Parcours B : installer RKE2 avec un rôle AnsibleParcours B
Rôle rke2TokenHAkube-vip
# ansible/inventory/rke2.yml all: vars: ansible_user: ops rke2_channel: v1.36 rke2_api_name: rke2.lab.local # DNS -> 10.0.0.50 rke2_token: "{{ vault_rke2_token }}" # dans group_vars/all/vault.yml chiffré children: rke2_first: { hosts: { rke2-s1: { ansible_host: 10.0.0.51 } } } rke2_servers: { hosts: { rke2-s2: { ansible_host: 10.0.0.52 }, rke2-s3: { ansible_host: 10.0.0.53 } } } rke2_agents: { hosts: { rke2-w1: { ansible_host: 10.0.0.54 } } }
# ansible/roles/rke2/tasks/main.yml (extrait) - name: Préparer l'hôte (swap, modules) ansible.builtin.shell: | swapoff -a modprobe br_netfilter overlay changed_when: false - name: Créer le dossier de config ansible.builtin.file: { path: /etc/rancher/rke2, state: directory, mode: "0755" } - name: config.yaml ansible.builtin.template: src: "{{ 'config-first.yaml.j2' if inventory_hostname in groups['rke2_first'] else 'config-join.yaml.j2' }}" dest: /etc/rancher/rke2/config.yaml mode: "0600" - name: Installer RKE2 ansible.builtin.shell: > curl -sfL https://get.rke2.io | INSTALL_RKE2_CHANNEL={{ rke2_channel }} INSTALL_RKE2_TYPE={{ 'agent' if inventory_hostname in groups['rke2_agents'] else 'server' }} sh - args: { creates: /usr/local/bin/rke2 } - name: Démarrer le service ansible.builtin.systemd: name: "{{ 'rke2-agent' if inventory_hostname in groups['rke2_agents'] else 'rke2-server' }}" enabled: true state: started
# templates/config-first.yaml.j2 token: {{ rke2_token }} tls-san: - {{ rke2_api_name }} - 10.0.0.50 secrets-encryption: true # templates/config-join.yaml.j2 (serveurs 2 et 3, et agent) server: https://{{ rke2_api_name }}:9345 token: {{ rke2_token }} tls-san: - {{ rke2_api_name }}
  1. Jouer le rôle sur rke2_first seul, attendre que le nœud soit Ready (kubectl get nodes)
  2. Jouer sur rke2_servers avec serial: 1 (un nœud à la fois)
  3. Jouer sur rke2_agents
  4. Récupérer /etc/rancher/rke2/rke2.yaml, remplacer 127.0.0.1 par rke2.lab.local
Point dur : l'API doit répondre sur rke2.lab.local avant que les serveurs 2 et 3 ne rejoignent. Pour le labo, fais pointer le DNS vers rke2-s1 au début, puis installe kube-vip (ou un HAProxy) pour l'IP 10.0.0.50 une fois le cluster formé. Le shell + creates ci-dessus est volontairement simple : à transformer en rôle propre ensuite.

  1. Se connecter, changer le mot de passe d'amorçage, vérifier l'URL du serveur (Global Settings : server-url = https://rancher.lab.local)

  3. Tester la connexion avec un compte de test avant d'activer (Rancher peut restreindre l'accès aux utilisateurs autorisés)
  4. Créer des rôles globaux et attribuer des groupes : administrateurs, lecture seule, équipes applicatives
  5. Créer des projets (regroupements de namespaces) avec quotas et rôles de projet

9Rancher : créer et importer des clusters downstreamRancher
CustomImportAgentNœuds

Option 1 : cluster RKE2 « custom » sur des VM créées par Terraform

  1. Créer 3 VM supplémentaires par Terraform (ds-s1, ds-w1, ds-w2), comme dans le parcours B
  2. Dans Rancher : Cluster Management → Create → Custom (RKE2 / K3s), choisir la version de Kubernetes proposée, le CNI, nommer le cluster
  3. Rancher affiche une commande d'enregistrement (rôles à cocher : etcd, control plane, worker) à lancer sur chaque VM
  4. Automatiser cette commande avec Ansible (un rôle rancher-register) : elle contient un jeton, à passer par Vault
  5. Suivre l'état du cluster dans l'interface jusqu'à Active
# Forme indicative : la commande réelle (avec jeton et options) vient de l'interface Rancher curl -fL https://rancher.lab.local/system-agent-install.sh | sudo sh -s - \ --server https://rancher.lab.local --label 'cattle.io/os=linux' \ --token JETON --etcd --controlplane --worker

Option 2 : importer un cluster existant

# Rancher → Import Existing → Generic : copier la commande fournie par l'interface kubectl apply -f https://rancher.lab.local/v3/import/XXXXX.yaml kubectl -n cattle-system get pods # attendre cattle-cluster-agent Running
CasChoix
Cluster créé et exploité par RancherCustom (ou fournisseur d'infrastructure) : Rancher gère les mises à jour de version
Cluster existant (RKE2 du parcours B, autre distribution)Import : Rancher observe et gère l'accès, mais pas le cycle de vie du cluster
Beaucoup de VM à créer à la demandeFournisseur d'infrastructure supporté (vSphere, Harvester, cloud) ; pour Proxmox : Terraform + custom, ou un pilote communautaire à évaluer
Ne mélange pas les méthodes de mise à jour : un cluster provisionné par Rancher se met à jour depuis Rancher ; un cluster importé se met à jour avec ses propres outils.
10Rancher : GitOps avec Fleet, monitoring et sauvegardeRancher

Fleet : déployer depuis Git sur plusieurs clusters

  1. Créer un dépôt Git d'applications (base/ + dossiers par environnement)
  2. Continuous Delivery → Git Repos → Add (ou un objet GitRepo dans le namespace fleet-default)
  3. Cibler les clusters par labels (env=prod, env=test)
  4. Modifier le dépôt, observer la synchronisation ; faire un git revert pour revenir en arrière
apiVersion: fleet.cattle.io/v1alpha1 kind: GitRepo metadata: { name: apps, namespace: fleet-default } spec: repo: https://git.lab.local/infra/apps.git branch: main paths: [ base ] targets: - clusterSelector: { matchLabels: { env: test } }

Monitoring et journaux

  • Apps → Charts : installer Monitoring (Prometheus + Grafana) et, si besoin, Logging sur chaque cluster concerné
  • Définir 3 alertes utiles : nœud NotReady, disque > 85 %, redémarrages de Pods en boucle
  • Vérifier le stockage des métriques (volume persistant, rétention) pour ne pas remplir un disque

Sauvegarde de Rancher lui-même

  • Installer l'opérateur Rancher Backups depuis le catalogue, créer une sauvegarde planifiée vers un stockage S3 (MinIO en labo)
  • Tester une restauration sur un cluster vierge : c'est la seule preuve
  • En plus : snapshots etcd du cluster qui héberge Rancher (fiche RKE2, section 8)
  • Nom exact des charts et des objets : à vérifier dans la documentation de ta version.

Auto-évaluation — clique pour voir la réponse

Pourquoi combiner Terraform et Ansible ?

Terraform crée l'infrastructure (VM, réseau) de façon déclarative ; Ansible configure l'intérieur (paquets, services, RKE2). Chacun a son domaine.

Qu'est-ce que l'idempotence dans Ansible ?

Rejouer un playbook ne change rien si l'état voulu est déjà atteint (changed=0).

À quoi servent --check et --diff ?

Simuler sans appliquer et afficher les différences prévues.

Comment éviter les secrets dans Git ?

Variables d'environnement, tfvars ignoré, Ansible Vault, gestionnaire de secrets.

Pourquoi utiliser for_each avec un map ?

Pour créer plusieurs ressources similaires, chacune identifiée par une clé stable (ajouter ou retirer une VM ne touche pas les autres).

Que fait cloud-init sur une VM clonée ?

Applique au premier démarrage le nom, l'IP, l'utilisateur et la clé SSH.

Pourquoi 3 serveurs RKE2 ?

Pour le quorum etcd : la perte d'un serveur est tolérée.

Pourquoi jouer serial: 1 sur les serveurs ?

Pour qu'ils rejoignent un à un et garder le quorum stable.

À quoi sert tls-san ?

Inclure dans le certificat de l'API tous les noms et IP par lesquels on la joint.

Pourquoi une IP virtuelle pour l'API ?

Pour un point d'entrée unique qui survit à la perte d'un serveur (kube-vip ou load balancer).

Quels sont les prérequis de l'installation Helm de Rancher ?

Un cluster RKE2 sain, cert-manager, un nom DNS, le dépôt Rancher et un mot de passe d'amorçage.

Comment mesurer un RTO d'infrastructure avec ce labo ?

Détruire puis reconstruire par Terraform et Ansible en chronométrant le retour d'un cluster fonctionnel.

Que sauvegarder en plus du code ?

Les snapshots etcd, les volumes (Velero ou outil du stockage), le state Terraform et les VM (PBS).

Quel est le risque d'un seul nœud Proxmox ?

Un point de défaillance commun : toutes les VM du cluster tombent ensemble ; répartir sur plusieurs nœuds en vrai.

Quelle différence entre cluster custom et cluster importé dans Rancher ?

Custom : Rancher provisionne et gère le cycle de vie (versions). Importé : Rancher se connecte à un cluster existant via un agent, sans gérer ses mises à jour.

Comment Rancher parle-t-il aux clusters downstream ?

Par le cattle-cluster-agent déployé dans le cluster cible, qui se connecte à Rancher en HTTPS (443).

Pourquoi attribuer les rôles par groupes de l'annuaire ?

Les arrivées et départs se gèrent dans l'annuaire, sans toucher aux droits dans Rancher.

Pourquoi garder un compte local de secours ?

Pour pouvoir administrer Rancher si le fournisseur d'identité est indisponible.

À quoi sert Fleet et comment cibler des clusters ?

GitOps intégré : un GitRepo est déployé sur les clusters sélectionnés par labels (clusterSelector).

Que sauvegarder pour reconstruire Rancher ?

L'opérateur Rancher Backups vers S3, les snapshots etcd du cluster hôte, les values Helm et le code Terraform / Ansible dans Git.

Quand utiliser l'inventaire dynamique Proxmox ?

Quand les VM sont créées par code : l'inventaire se construit depuis l'API plutôt qu'à la main.
