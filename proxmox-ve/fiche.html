Qu'est-ce que Proxmox VE ?

  • Plateforme de virtualisation 100 % open source, basée sur Debian GNU/Linux
  • Deux technologies : KVM (machines virtuelles) et LXC (conteneurs système)
  • Gestion centralisée en multi-maître : on peut administrer tout le cluster depuis n'importe quel nœud
  • Fonctions intégrées : sauvegarde, HA, SDN, pare-feu, Ceph, ZFS

VM (KVM) vs conteneur (LXC)

  • VM : matériel émulé, noyau et OS propres, n'importe quel OS (Windows, Linux, BSD…), isolation forte
  • LXC : partage le noyau de l'hôte, démarrage rapide, peu de ressources, Linux uniquement
  • Isolation d'un conteneur plus faible : surface d'attaque = noyau de l'hôte
  • Règle pratique : VM pour Windows/isolation, LXC pour services Linux légers

Les démons à connaître

  • pveproxy : proxy API / interface web (port 8006)
  • pvedaemon : démon API (actions privilégiées)
  • pvestatd : collecte des statuts et métriques
  • pvescheduler : tâches planifiées (sauvegardes, réplications)
  • pve-cluster (pmxcfs) + corosync : cluster
  • pve-firewall, pve-ha-crm / pve-ha-lrm

pmxcfs en une phrase

  • Système de fichiers de configuration du cluster, monté sur /etc/pve
  • Basé sur une base de données, répliqué en temps réel entre nœuds via corosync
  • Taille maximale 128 Mio, tenu en RAM : on n'y met que de la config
  • Conséquence : modifier un fichier dans /etc/pve sur un nœud le modifie partout

Types de stockage supportés (vue rapide)

Réseau : NFS, CIFS, iSCSI, LVM sur iSCSI, Ceph RBD, CephFS, Proxmox Backup Server. Local : répertoire, LVM, LVM-thin, ZFS, Btrfs.

À retenir : Proxmox VE = Debian + noyau Proxmox + outils (qm, pct, pvesm, pvecm…) + interface web. Tout ce que fait l'interface passe par l'API REST, donc par pvesh aussi.

Méthodes et systèmes de fichiers

Méthodes

  • ISO sur clé USB (recommandé) ou CD/DVD
  • Sur un Debian existant (ajout des dépôts Proxmox)
  • Installation automatisée : fichier de réponses + ISO préparée

Système de fichiers de l'OS

  • ext4 (défaut) ou XFS sur LVM
  • ZFS : RAID logiciel (stripe, miroir, RAIDZ…), disques à choisir dans les options
  • Btrfs : aperçu technologique

Disposition LVM par défaut

  • Groupe de volumes pve
  • LV root et swap + pool thin data
  • Stockages créés : local (répertoire) et local-lvm (LVM-thin)

Options de l'installateur LVM

  • hdsize : taille de disque utilisée
  • swapsize : taille du swap (0 = pas de swap)
  • maxroot : taille max du volume root
  • minfree : espace libre laissé dans le VG
  • maxvz : taille max du volume de données

Après l'installation

  • Ouvrir https://adresse-ip:8006, se connecter en root (realm PAM) avec le mot de passe choisi
  • Soit charger une clé d'abonnement (dépôt Enterprise), soit configurer les dépôts publics no-subscription
  • Vérifier IP, nom d'hôte, fuseau horaire et pare-feu
Nom d'hôte : le changer après la création d'un cluster est délicat. Choisis un FQDN propre dès l'installation.

5Réseau et SDNBridges, bonds, VLAN
vmbr0/etc/network/interfacesSDN

Principe

  • Configuration dans /etc/network/interfaces (modifiable aussi via l'interface)
  • Les invités se branchent sur un pont Linux (vmbr0) relié à la carte physique
  • Appliquer sans redémarrer : ifreload -a

Conventions de noms

  • Cartes : en* ou eth[N]
  • Ponts : vmbr[N]
  • Agrégats : bond[N]
  • VLAN : numéro après un point : eno1.50, bond1.30

Modes de bonding

  • active-backup : basculement simple, aucun réglage côté switch
  • 802.3ad (LACP) : agrégation, switch compatible requis
  • balance-rr, balance-xor, broadcast, balance-tlb, balance-alb

VLAN

  • Standard IEEE 802.1q
  • Pont « VLAN aware » + étiquette VLAN sur la carte virtuelle de l'invité
  • Permet plusieurs réseaux isolés sur un seul pont

Exemple de pont (/etc/network/interfaces)

auto vmbr0 iface vmbr0 inet static address 192.168.1.10/24 gateway 192.168.1.1 bridge-ports eno1 bridge-stp off bridge-fd 0

SDN (Software-Defined Network)

Type de zonePrincipeÀ retenir
SimplePont isolé par nœudPas de lien entre nœuds ; souvent avec NAT/DHCP
VLANUtilise les VLAN d'un pont existantDemande que le switch laisse passer les VLAN
QinQDouble étiquetage 802.1adPour les fournisseurs / empilement de VLAN
VXLANTunnels L2 sur réseau L3 (UDP)Relie des nœuds sans VLAN commun
EVPNVXLAN + BGP (routage)Le plus complexe ; utilise FRR

Vocabulaire SDN : zone (type de réseau) → VNet (réseau virtuel visible par les invités) → sous-réseau. S'ajoutent contrôleurs, IPAM et DHCP. La configuration est dans /etc/pve/sdn et doit être appliquée depuis le panneau SDN pour prendre effet.

Piège : une mauvaise modification du réseau de gestion peut te couper de l'interface. Garde un accès console (iDRAC/IPMI, écran) avant de toucher à vmbr0.

Types de contenu

  • images : disques de VM
  • rootdir : disques de conteneurs
  • vztmpl : modèles de conteneurs
  • iso : images d'installation
  • backup : sauvegardes vzdump
  • snippets : fichiers (cloud-init, hookscripts)

Pourquoi du stockage partagé ?

  • Migration à chaud sans copier les disques
  • Redémarrage rapide des invités HA sur un autre nœud
  • Alternative sans stockage partagé : réplication ZFS

Thin provisioning

  • Disponible partout où les snapshots existent : LVM-thin, ZFS, qcow2, Ceph
  • On alloue plus que l'espace réel : surveiller le remplissage, un pool thin plein fige les VM
pvesm status # état des stockages pvesm list local # contenu d'un stockage pvesm add nfs nas --server 10.0.0.5 --export /data --content backup,iso pvesm set nas --disable 1 # désactiver sans supprimer pvesm path local:iso/debian.iso # chemin réel d'un volume
LVM vs LVM-thin : les snapshots LVM classiques dégradent fortement les écritures du groupe de volumes ; depuis PVE 9 existent des « snapshots en chaîne de volumes » pour les VM. Le LVM-thin gère les snapshots efficacement mais n'est pas partagé : c'est pourquoi on y met les disques locaux (local-lvm).
Fichiers qcow2 : sur les stockages à fichiers (répertoire, NFS, CIFS), les snapshots passent par le format qcow2. Créer ou supprimer un snapshot interne peut bloquer une VM en marche, très lentement sur NFS pour de gros disques : préfère le faire VM éteinte.

Approfondissement : bloc ou fichier, thick ou thin

Stockage fichier

  • Répertoire, NFS, CIFS, CephFS
  • Les disques sont des fichiers (raw, qcow2, vmdk) ; qcow2 recommandé pour avoir toutes les fonctions
  • Stocke aussi ISO, modèles, sauvegardes, snippets
  • Les snapshots viennent du format qcow2

Stockage bloc

  • ZFS, LVM, LVM-thin, Ceph RBD, iSCSI
  • Les disques sont des volumes bruts (zvol, LV, image RBD)
  • Les snapshots et clones sont fournis par la couche de stockage elle-même
  • Pas d'ISO ni de sauvegardes sur ces types (sauf répertoire par-dessus)

Local ou partagé

  • Local : le même nom existe sur tous les nœuds mais le contenu est différent ; restreindre aux bons nœuds avec la liste de nœuds du stockage
  • Partagé : même contenu partout (NFS, Ceph…) ; le drapeau shared dit au cluster qu'un mécanisme externe garantit l'accès
  • Montage non géré : pvesm set STOCKAGE --is_mountpoint 1 évite d'écrire sur le disque de l'hôte si le montage est absent

Question d'examen classique : « Mon pool thin est plein, toutes mes VM plantent ». Le thin provisioning est une promesse de place, pas de la place. Surveille lvs (colonnes Data% et Meta%) ou zpool list.

Chaîne de volumes (volume chain)

  • Chaque snapshot = un nouveau volume posé en couche sur le précédent (chaînage qcow2)
  • qcow2 ne sert qu'à chaîner ; la gestion est faite par Proxmox, pas par les snapshots internes qcow2
  • Efficace seulement si le stockage sous-jacent est thin et supporte discard
  • Les volumes de snapshot sont des LV épais
  • Limite : avec un TPM, le snapshot le plus récent ne peut pas être supprimé VM allumée

Stockage SAN/NAS existant : les options

  • Recommandation officielle : Ceph pour le partagé
  • Une grosse LUN iSCSI/FC + LVM épais partagé (+ multipath)
  • Un partage NFS/CIFS + qcow2 (snapshots possibles)
  • Plugin du constructeur, ou ZFS sur iSCSI
  • Déconseillé : une LUN par disque (charge manuelle)

Alternative aux snapshots

  • Avec Proxmox Backup Server : sauvegardes rapides (suivi des blocs modifiés) et live-restore (la VM démarre pendant la restauration)
  • Pratique quand le stockage ne sait pas faire de snapshot

  • Clone complet : copie indépendante
  • Clone lié : s'appuie sur le modèle (rapide, économe), le modèle ne peut plus être supprimé

Cloud-init

  • Disque spécial : qm set 9000 --ide2 local-lvm:cloudinit
  • Paramètres : ciuser, cipassword, sshkeys, ipconfig0
  • Idéal pour industrialiser : modèle + clone + cloud-init

Passthrough PCI(e)

  • Donne un périphérique physique (GPU, carte réseau) à une VM
  • Prérequis : IOMMU activée (VT-d / AMD-Vi), machine q35, OVMF
  • qm set 100 -hostpci0 02:00,pcie=on
  • La VM ne peut plus être migrée à chaud
qm create 100 --name web --memory 4096 --cores 2 --net0 virtio,bridge=vmbr0 qm start 100 ; qm shutdown 100 ; qm stop 100 # shutdown = propre, stop = coupure brutale qm clone 9000 101 --name web2 --full qm snapshot 100 avant-maj ; qm rollback 100 avant-maj qm resize 100 scsi0 +10G # agrandir un disque (jamais réduire) qm move-disk 100 scsi0 local-lvm # migrer un disque vers un autre stockage qm config 100 # afficher la configuration qm migrate 100 pve2 --online
Ordre de démarrage : onboot: 1 démarre la VM avec le nœud ; startup: order=1,up=30,down=60 règle l'ordre et les délais.
Snapshots : ils sont pratiques avant une mise à jour mais ne remplacent pas une sauvegarde (même stockage que le disque). Un snapshot « avec RAM » capture aussi l'état en mémoire.

Snapshots de VM en détail

Ce qu'est un snapshot

  • État des disques + configuration de la VM à un instant donné
  • La config est conservée dans une section [nom] du fichier .conf
  • Option « inclure la RAM » (--vmstate 1) : on revient à une VM en marche, état mémoire compris (le fichier d'état demande de la place)

Rollback et suppression

  • qm rollback remet disques et config à l'état du snapshot : les modifications faites depuis sont perdues
  • Revenir à un snapshot ancien implique souvent de supprimer les plus récents (selon le stockage)
  • Supprimer un snapshot fusionne ses changements, ce n'est pas une annulation

Quand les éviter

  • Snapshots conservés longtemps : espace consommé et performances dégradées (surtout qcow2 interne, LVM classique)
  • Pas un backup : même stockage que le disque, perdu avec lui
  • VM avec périphérique PCI en passthrough : pas de snapshot avec RAM
qm snapshot 100 avant-maj --vmstate 1 --description "avant mise à jour" qm listsnapshot 100 qm rollback 100 avant-maj qm delsnapshot 100 avant-maj pct snapshot 200 avant-maj ; pct rollback 200 avant-maj # conteneurs : stockage compatible requis
8Conteneurs LXCpct, pveam
LXCModèlesNon privilégié

Principe

  • Un conteneur utilise le noyau de l'hôte : démarrage en secondes, très peu de surcharge
  • Fichier : /etc/pve/lxc/<CTID>.conf
  • Seulement des distributions Linux
  • Conteneurs « système » (le cas courant) ; conteneurs « application » OCI en aperçu technologique

Privilégié vs non privilégié

  • Non privilégié (défaut) : root du conteneur = utilisateur sans droits sur l'hôte (user namespaces)
  • Privilégié : considéré peu sûr ; seulement en environnement de confiance
  • Préférer toujours le non privilégié

Fonctionnalités (features)

  • nesting : conteneurs imbriqués, requis par systemd
  • keyctl : appel système nécessaire pour Docker dans un conteneur non privilégié
  • fuse : systèmes de fichiers FUSE

Points de montage

  • rootfs + mp0 à mp255
  • Sur stockage : géré par Proxmox (snapshots, redimensionnement)
  • Bind mount : dossier de l'hôte, hors stockage (pas de snapshot, soucis de droits UID en non privilégié)
  • Ne jamais monter /, /etc ou /var de l'hôte

Prérequis du cluster

  • Les nœuds se joignent en UDP 5405-5412 (corosync) et par SSH TCP 22
  • Heure synchronisée, même version de Proxmox VE sur tous les nœuds
  • Réseau corosync à faible latence, idéalement dédié ; corosync accepte jusqu'à 8 liens (redondance)

pvecm create MONCLUSTER --link0 10.10.10.1 # sur le premier nœud pvecm add 10.10.10.1 # sur chaque nœud qui rejoint pvecm status ; pvecm nodes # état du quorum, liste des nœuds pvecm delnode ancien-noeud # retirer un nœud (éteint, hors cluster) pvecm qdevice setup 10.0.0.9 # ajouter un arbitre externe pvecm expected 1 # DANGER : forcer le quorum à 1 vote

Le quorum

Définition

  • Nombre minimal de votes pour qu'une opération soit autorisée : la majorité (N/2 + 1)
  • Sans quorum, le cluster passe en lecture seule : plus de démarrage d'invité ni de changement de config

Cluster à 2 nœuds

  • Perdre un nœud = perdre la majorité → blocage
  • Solution : un QDevice (troisième voix sur un petit serveur ou une VM externe)
  • Pour la HA, viser 3 vrais nœuds

pvecm expected 1

  • Débloque un nœud isolé en abaissant le seuil de quorum
  • À n'utiliser qu'en dépannage, jamais avec deux moitiés du cluster actives : risque de split-brain

Fichiers utiles

  • /etc/pve/corosync.conf (copie cluster)
  • /etc/corosync/corosync.conf (copie locale)
  • /etc/pve = pmxcfs, en lecture seule sans quorum
Piège : un nœud retiré avec pvecm delnode ne doit jamais revenir tel quel sur le même réseau : il faut le réinstaller (ses ID et sa configuration entreraient en conflit).

Approfondissement cluster

Réseau corosync : chiffres à connaître

  • Latence stable et inférieure à 5 ms recommandée ; au-delà de 10 ms, une exploitation stable est improbable avec plus de 3 nœuds
  • Faible débit mais très sensible à la gigue : une carte 1 Gbit dédiée suffit
  • Ne pas partager avec le stockage, les sauvegardes ou la migration : ils saturent le lien
  • Jusqu'à 8 liens (transport kronosnet) : --link0, --link1, avec priority par lien

Rejoindre un cluster : ce qui se passe

  • pvecm add IP-DU-CLUSTER (ou depuis l'interface), avec --link0 IP-LOCALE si réseau cluster séparé
  • Authentification par défaut via l'API : mot de passe root@pam d'un nœud existant + vérification de l'empreinte SHA-256 du certificat
  • La config de /etc/pve du nœud est écrasée ; il hérite des stockages du cluster
  • Son certificat est remplacé par un certificat signé par la CA du cluster
  • Conflit d'ID si des invités existent déjà : les sauvegarder (vzdump), puis restaurer avec un autre ID après l'adhésion

Votes et QDevice

  • 1 vote par nœud par défaut (corosync_votequorum)
  • QDevice : corosync-qnetd sur un serveur externe indépendant, corosync-qdevice sur chaque nœud
  • Algorithme ffsplit : en cas d'égalité, la partition au plus petit ID de nœud l'emporte
  • Nombre pair de nœuds : idéal (+1 voix) ; nombre impair : déconseillé (N-1 voix → le qnetd devient un point de défaillance)

Chronologie d'une panne (HA)

  • Chaque nœud HA signale sa présence toutes les 10 s
  • Si un nœud disparaît, le cluster attend ~2 minutes avant de relancer ses invités HA ailleurs
  • Un nœud vivant qui perd le quorum attend ~1 minute puis se fence lui-même (équivalent d'un reset)
  • Si tous les nœuds ont le même problème de corosync, tout le cluster semble redémarrer d'un coup

Quorum et corosync en détail

Rôles : corosync assure la communication entre nœuds (protocole Totem, transport kronosnet, en unicast) et le calcul du quorum (module votequorum). pmxcfs (service pve-cluster) utilise ce quorum pour savoir si /etc/pve peut être écrit. Sans quorum : les VM déjà en marche continuent de tourner, mais on ne peut plus démarrer d'invité ni modifier la configuration.

Le calcul du quorum

Le quorum est la majorité stricte des votes attendus : quorum = ⌊votes / 2⌋ + 1. Une partition du cluster ne peut agir que si elle a la majorité : c'est ce qui évite le split-brain (deux moitiés qui démarrent chacune la même VM).

Anatomie de corosync.conf

totem { version: 2 cluster_name: moncluster config_version: 7 # À INCRÉMENTER à chaque modification ip_version: ipv4-6 secauth: on interface { linknumber: 0 knet_link_priority: 20 # priorité du lien (le plus élevé est préféré) } interface { linknumber: 1 knet_link_priority: 10 } } nodelist { node { name: pve1 nodeid: 1 quorum_votes: 1 ring0_addr: 10.10.10.1 # lien 0 (réseau corosync dédié) ring1_addr: 192.168.1.11 # lien 1 (secours) } # ... un bloc node par nœud } quorum { provider: corosync_votequorum } logging { to_syslog: yes }

  • ring0_addr peut être une IP ou un nom ; préférer des IP pour ne pas dépendre du DNS
  • Chaque lien est un réseau physique distinct de préférence ; kronosnet bascule automatiquement sur un autre lien si l'un tombe

QDevice : mise en place

  1. Un serveur externe et indépendant du cluster (petite VM ailleurs, Raspberry, machine d'un autre site) avec corosync-qnetd
  2. Sur tous les nœuds : apt install corosync-qdevice
  3. Depuis un nœud : pvecm qdevice setup IP-DU-QNETD (accès SSH root vers le serveur nécessaire pendant l'installation)
  4. Vérifier avec pvecm status : une ligne Qdevice apparaît et le total de votes augmente
  5. Retirer : pvecm qdevice remove
  • Le QDevice ne remplace pas un nœud : il donne seulement une voix de départage
  • Ne jamais l'héberger sur une VM du cluster qu'il arbitre
  • Il doit être joignable par TCP depuis chaque nœud (port 5403 du service qnetd)

Bonnes pratiques corosync (checklist)

  • Réseau corosync dédié (VLAN ou NIC propre), pas partagé avec stockage / sauvegarde / migration
  • Deux liens au minimum, sur des switchs différents quand possible, avec priorités définies
  • Latence stable < 5 ms ; surveiller la gigue plus que le débit
  • MTU cohérent sur tout le chemin ; ouvrir UDP 5405-5412 entre nœuds si pare-feu
  • NTP synchronisé ; IP et noms de nœuds stables (ne pas les changer après création)
  • Nombre de nœuds impair, ou pair + QDevice
  • Documenter la procédure de reprise (pvecm expected, delnode) et la tester en labo
  • Sauvegarder /etc/pve/corosync.conf avant toute modification

Procédures d'exploitation

Retirer un nœud proprement

  • 1. Migrer ou supprimer tous les invités, sauvegarder les données locales
  • 2. Le sortir des jobs de réplication ; si Ceph : détruire OSD, MDS, MON, MGR et retirer le bucket CRUSH (attendre HEALTH_OK)
  • 3. Éteindre le nœud et s'assurer qu'il ne reviendra pas sur le réseau
  • 4. Depuis un autre nœud : pvecm delnode nœud, puis pvecm nodes
  • 5. Nettoyer /etc/pve/nodes/nœud

Séparer sans réinstaller (déconseillé)

  • Résoudre d'abord le stockage partagé
  • systemctl stop pve-cluster corosync puis pmxcfs -l (mode local)
  • Supprimer /etc/pve/corosync.conf et /etc/corosync/*, relancer pve-cluster
  • pvecm delnode depuis l'autre côté, nettoyer /var/lib/corosync/*
  • Procédure risquée : la réinstallation reste la méthode sûre

Modifier corosync.conf sans casser

  • Copier en corosync.conf.new, éditer cette copie
  • Toujours incrémenter config_version dans la section totem
  • Garder une sauvegarde corosync.conf.bak, puis remplacer le fichier
  • Redémarrer corosync si les changements ne sont pas pris en compte

Cas particuliers

  • Hostname et IP d'un nœud : non modifiables après la création du cluster
  • Démarrage à froid (panne électrique totale) : pas de quorum tant que les nœuds ne sont pas revenus ; le service pve-guests attend le quorum puis démarre les invités onboot
  • Plage de VMID automatique : Datacenter → Options → Next free VMID range
  • Abonnement : chaque nœud a le sien, tous au même niveau

  • Affinité de ressources : positive = « rester ensemble sur le même nœud », négative = « rester séparées » (utile pour deux contrôleurs redondants)

Principe

  • Copie périodique des disques d'un invité vers un autre nœud, par snapshots ZFS incrémentaux
  • ZFS local uniquement, même nom de pool sur la source et la cible
  • Planification en calendrier systemd ; intervalle de 1 minute à 1 semaine

  • Environ 8 Gio de RAM par OSD pour de bonnes performances
  • SSD/NVMe et contrôleur HBA, pas de RAID matériel

Réplication des pools

  • Défaut : size 3 (trois copies) et min_size 2 (E/S possibles tant que 2 copies existent)
  • Règles CRUSH : placement des données, par classe de disque (hdd, ssd, nvme)
  • États de santé : HEALTH_OK, HEALTH_WARN, HEALTH_ERR

Préparation de la VM source

À faire AVANT la migration

  • Désinstaller VMware Tools (plus dur à retirer après)
  • Noter la configuration réseau (IP, DNS, passerelle)
  • Windows : envisager de retirer l'IP statique, sinon avertissement d'IP en double sur le nouvel adaptateur
  • DHCP : adapter la réservation à la nouvelle adresse MAC, ou fixer la MAC sur la carte de la VM cible
  • Chiffrement de disque : l'état vTPM n'est pas migrable ; désactiver, ou garder les clés manuelles
  • Éteindre la VM source pour un état cohérent

VM cible : bonnes pratiques

  • BIOS : SeaBIOS si la source démarre en legacy, OVMF si elle démarre en UEFI (+ disque EFI)
  • CPU : host si tous les nœuds sont identiques, sinon x86-64-v2-AES ou supérieur
  • Disques : bus SCSI + contrôleur VirtIO SCSI single, discard et IO thread activés
  • Réseau : VirtIO (modèle E1000 pour anciens OS sans pilote)
  • Mémoire : activer le ballooning (même inutile, il remonte l'usage réel)
  • Agent : installer qemu-guest-agent

Méthode 1 — Import automatique depuis ESXi (pas à pas)

  1. Proxmox VE en version 8 ou plus, à jour
  2. Datacenter → Storage → Add → ESXi : adresse de l'hôte ESXi et identifiants d'un compte admin. Certificat auto-signé : ajouter la CA ou cocher Skip Certificate Verification
  3. Préférer l'hôte ESXi directement : passer par vCenter réduit fortement les performances
  4. Sélectionner ce stockage dans l'arbre : le panneau Import liste les VM disponibles
  5. Choisir la VM → Import ; régler au minimum le stockage cible des disques et le pont réseau
  6. Onglet Advanced : stockage par disque, modèle de carte réseau, ISO du lecteur, ne pas importer certains disques / cartes
  7. Onglet Resulting Config : vérifier la configuration générée
  8. Terminer la préparation, éteindre la VM côté ESXi, lancer l'import
  9. Démarrer la VM et traiter les points de la section post-migration
  • Testé depuis ESXi 6.5 jusqu'à 8.0
  • Live-import : la VM démarre pendant l'import (les données nécessaires au démarrage arrivent d'abord, le reste en arrière-plan). La VM ESXi reste éteinte, donc il y a quand même un arrêt. Légère perte de performances au début. En cas d'échec, tout ce qui a été écrit depuis le démarrage est perdu : à tester d'abord, à éviter sur réseau lent ou instable
  • Import en masse : sérialiser les imports, pas plus de 4 disques en parallèle. Limites : nombre de connexions de l'API ESXi (au-delà, blocage d'environ 30 s, parfois erreurs 503 → ajuster Config.HostAgent.vmacore.soap.maxSessionCount) et mémoire (cache de lecture : 8 blocs de 128 Mio par disque)

Méthode 2 — Export OVF puis qm importovf

# Sur l'hôte Proxmox : exporter depuis un ESXi (ovftool de VMware, version compatible) apt install unzip ./ovftool vi://root@ESXI-IP/NOM-VM /chemin/export # ou depuis vCenter ./ovftool vi://USER:MDP@VCENTER/DATACENTER/vm/NOM-VM /chemin/export # Importer (VMID libre, stockage avec contenu « Disk Image ») qm importovf 100 Server.ovf local-zfs qm importovf 100 Server.ovf nas --format qcow2 # format raw | vmdk | qcow2 sur stockage fichier qm set 100 --cpu x86-64-v2-AES --scsihw virtio-scsi-single

Après l'import, il faut ajouter une carte réseau et aligner la VM sur les bonnes pratiques. Pour une VM Windows, repasser d'abord le disque en IDE ou SATA (détacher le disque « Unused », le rattacher sur ce bus).

Méthode 3 — Import de disque (qm disk import)

  1. Rendre les fichiers *.vmdk et *-flat.vmdk accessibles (partage NFS/SMB déclaré comme stockage, ou copie)
  2. Créer la VM cible à la main et supprimer le disque par défaut
  3. Importer : le disque est converti au format cible à la volée
  4. Le disque apparaît en unusedX : l'attacher sur un bus, l'activer dans l'ordre de démarrage
cd /mnt/pve/NOM-STOCKAGE/NOM-VM qm disk import 104 Server.vmdk local-zfs # ancien nom : qm importdisk qm disk import 104 Server.vmdk nas --format qcow2 qm set 104 --scsi0 local-zfs:vm-104-disk-0,discard=on,iothread=1 qm set 104 --boot order=scsi0

Méthode 4 — Attach & Move Disk (arrêt minimal)

Idée : démarrer la VM Proxmox directement sur le VMDK posé sur un partage commun, puis déplacer le disque vers le stockage définitif VM allumée.

  1. Déclarer le partage comme stockage Proxmox (contenu « Disk Image ») : monté sous /mnt/pve/NOM
  2. Créer la VM cible ; pour le disque système, choisir ce stockage au format vmdk (EFI et TPM sur le stockage définitif)
  3. Copier le .vmdk source par-dessus celui que Proxmox vient de créer ; laisser le -flat.vmdk en place
  4. Éditer le descripteur copié : la ligne « Extent description » doit pointer en chemin relatif vers le -flat.vmdk source
  5. Éteindre la VM côté VMware, puis démarrer côté Proxmox
  6. VM allumée : Disk Action → Move Storage vers le stockage cible
cp Server/Server.vmdk images/103/vm-103-disk-0.vmdk nano images/103/vm-103-disk-0.vmdk # avant : RW 104857600 VMFS "Server-flat.vmdk" # après : RW 104857600 VMFS "../../Server/Server-flat.vmdk"
Danger : ne jamais allumer la même VM côté VMware et côté Proxmox : corruption de disque assurée.

# Inspecter et vérifier qemu-img info Server.vmdk qemu-img check disque.qcow2 # VMDK -> qcow2 (progression, -p) qemu-img convert -p -f vmdk -O qcow2 Server.vmdk Server.qcow2 # VMDK / VHDX -> raw (pour LVM, ZFS, Ceph) ; -S 0 évite les fichiers creux qemu-img convert -p -f vhdx -O raw Server.vhdx Server.raw # Options utiles : compression, préallocation qemu-img convert -p -c -O qcow2 src.raw dst.qcow2 qemu-img convert -p -O qcow2 -o preallocation=metadata src.raw dst.qcow2 # Puis importer le résultat qm disk import 104 Server.qcow2 local-lvm # Export inverse : Proxmox -> VMware / Hyper-V qemu-img convert -p -f qcow2 -O vmdk -o subformat=streamOptimized disque.qcow2 out.vmdk qemu-img convert -p -f qcow2 -O vhdx disque.qcow2 out.vhdx
Thick → thin : convertir en qcow2 (ou importer vers LVM-thin / ZFS sparse) ne copie que les blocs utilisés quand les zéros sont détectés. Sur un disque raw déjà gros, la conversion qcow2 réduit la taille. Récupérer l'espace après coup : activer discard sur le disque de la VM, puis fstrim -av (Linux) ou Optimiser le lecteur / retrim (Windows) ; pour les disques sans TRIM, remplir de zéros (zerofree, sdelete -z) puis reconvertir.
  • La conversion nécessite de la place temporaire (source + destination) sur le stockage de travail ; convertir de préférence hors production
  • Toujours éteindre la VM source (ou la cloner) avant de convertir, pour un disque cohérent
  • Vérifier avec qemu-img info la taille virtuelle vs la taille réelle, puis qemu-img check
  • VM UEFI : prévoir un disque EFI et vérifier l'ordre de démarrage ; si le démarrage échoue, entrer dans le firmware de la VM (Échap/F2) pour re-sélectionner le fichier de démarrage
  • Conversions de VM entière (pilotes injectés automatiquement) : l'outil virt-v2v (libguestfs) existe mais n'est pas intégré à Proxmox ; la méthode standard reste l'assistant ESXi ou l'import + installation des pilotes

Pilotes VirtIO : Windows et Linux

Windows

  • Démarre « tel quel » seulement sur IDE ou SATA
  • Joindre l'ISO des pilotes VirtIO (lecteur CD supplémentaire), installer les pilotes
  • Procédure officielle pour basculer le disque de démarrage sur VirtIO SCSI (ajout d'un disque VirtIO temporaire pour charger le pilote avant de changer le bus du disque système)
  • Pilote réseau et ballooning à installer aussi

Linux

  • Les pilotes VirtIO sont dans le noyau ; vérifier qu'ils sont inclus dans l'initramfs avant migration
  • Sinon : démarrer en mode secours (initramfs plus complet), ou passer le bus du disque en IDE/SATA pour amorcer, puis régénérer l'initramfs
  • Nom d'interface réseau changé : mettre à jour la config (netplan, NetworkManager, ifcfg)

Après la migration

  • Mettre à jour la configuration réseau (le nom de la carte a changé)
  • Installer les pilotes manquants (VirtIO surtout sous Windows) et qemu-guest-agent
  • Retirer VMware Tools s'ils sont encore là
  • Activer l'agent dans les options de la VM, régler onboot et l'ordre de démarrage
  • Ajouter la VM aux sauvegardes et, si besoin, à la HA ; faire un test de restauration
  • Déplacer le disque vers son stockage définitif (Ceph, LVM-thin…) si ce n'est pas déjà fait
  • Garder la VM source éteinte, non supprimée, quelque temps (retour arrière possible)

VMware → Proxmox VE (les différences qui comptent)

  • Pas de vCenter : cluster multi-maître, on gère depuis n'importe quel nœud ; la perte du quorum bloque la config, pas les VM déjà en marche
  • Pas de VMFS : choisir le stockage selon le besoin (voir tableau des types) ; le datastore « partagé » classique devient NFS, Ceph ou LVM sur SAN
  • Snapshots : dépendent du stockage et pas d'un moteur unique ; un snapshot n'est pas disponible partout (voir matrice)
  • DRS / vMotion : migration à chaud OK, mais pas d'équilibrage automatique aussi poussé ; la HA redémarre les VM, ne les « migre » pas à chaud en cas de panne
  • Licences : logiciel libre (AGPL) ; l'abonnement donne accès au dépôt entreprise (mises à jour testées) et au support, par socket CPU

Auto-évaluation — clique pour voir la réponse

Quelles deux technologies de virtualisation Proxmox VE propose-t-il ?

KVM pour les machines virtuelles et LXC pour les conteneurs Linux.

Sur quel port écoute l'interface web ?

TCP 8006, en HTTPS.

Quelle est la différence entre le dépôt Enterprise et no-subscription ?

Enterprise est réservé aux abonnés (paquets les plus testés) ; no-subscription est gratuit mais moins testé. Sans abonnement, désactive Enterprise (erreur 401).

Pourquoi utiliser full-upgrade plutôt que upgrade ?

Parce qu'il peut installer ou supprimer des paquets pour résoudre les dépendances (noyau, paquets Proxmox).

Qu'est-ce que pmxcfs et où est-il monté ?

Le système de fichiers de configuration du cluster, basé sur une base de données répliquée par corosync, monté sur /etc/pve (128 Mio max, en RAM).

ZFS est-il compatible avec un contrôleur RAID matériel ?

Non : ZFS (comme Ceph) doit accéder directement aux disques (mode HBA).

Quels sont les stockages de VM locaux par défaut après installation ?

local (répertoire : ISO, sauvegardes, modèles) et local-lvm (LVM-thin : disques de VM et de conteneurs).

Quels types de stockage sont partagés ?

NFS, CIFS, iSCSI, Ceph RBD, CephFS, ZFS sur iSCSI et Proxmox Backup Server. LVM, LVM-thin, ZFS local, Btrfs et répertoire ne le sont pas.

Quel contrôleur disque et quelle carte réseau privilégier pour les performances d'une VM ?

VirtIO SCSI single (avec IO Thread) et carte réseau VirtIO.

Que faut-il pour le passthrough PCIe ?

IOMMU activée (VT-d / AMD-Vi), machine q35 et BIOS OVMF. La VM ne se migre plus à chaud.

Différence entre clone complet et clone lié ?

Le clone complet est une copie indépendante. Le clone lié partage les données du modèle (rapide, économe) mais dépend de lui.

À quoi sert l'agent invité QEMU ?

Arrêt propre, remontée de l'IP, gel du système de fichiers pendant une sauvegarde snapshot.

Pourquoi préférer un conteneur non privilégié ?

Le root du conteneur correspond à un utilisateur sans droits sur l'hôte (user namespaces) : un échappement est bien moins grave. Les privilégiés sont à réserver aux environnements de confiance.

Quelle fonctionnalité faut-il activer pour Docker dans un LXC non privilégié ?

keyctl=1, avec généralement nesting=1.

Quels ports et prérequis pour un cluster ?

UDP 5405-5412 (corosync), SSH 22, heure synchronisée, même version. Un nœud qui rejoint ne doit contenir aucun invité.

Qu'est-ce que le quorum et que se passe-t-il sans lui ?

La majorité des votes (N/2+1). Sans quorum, /etc/pve passe en lecture seule : plus de démarrage d'invités ni de modifications.

Comment faire fonctionner un cluster à deux nœuds de façon fiable ?

Ajouter un QDevice (pvecm qdevice setup) comme troisième voix.

Pourquoi pvecm expected 1 est-il dangereux ?

Il force le quorum à un vote : si les deux moitiés du cluster le font, elles écrivent chacune de leur côté (split-brain).

Quels sont les prérequis de la HA ?

3 nœuds minimum, stockage partagé (ou réplication), redondance matérielle, fencing par watchdog.

Rôles de pve-ha-crm et pve-ha-lrm ?

CRM : décisions globales du cluster, déplacements et fencing. LRM : exécute les services du nœud local.

Que devient un nœud HA qui perd le quorum ?

Si des services HA y sont actifs, le watchdog le fait redémarrer après environ 60 secondes ; ses services sont relancés ailleurs.

Quels sont les trois modes de vzdump et lequel préférer pour une VM ?

stop, suspend, snapshot. Snapshot pour une interruption quasi nulle (avec l'agent invité) ; stop pour la cohérence maximale.

Qu'apporte Proxmox Backup Server par rapport à un simple stockage vzdump ?

Déduplication par blocs, sauvegardes incrémentales rapides, chiffrement côté client, restauration de fichiers et live-restore.

Quelles conditions pour la réplication de stockage ?

ZFS local sur les deux nœuds, même nom de pool ; planification de 1 minute à 1 semaine ; peut perdre les dernières données en cas de HA.

Où s'active le pare-feu pour qu'une règle de VM s'applique ?

Au niveau Datacenter, au niveau de la VM, et sur la carte réseau virtuelle concernée.

Quelle est la politique par défaut du pare-feu ?

Entrée en DROP, sortie en ACCEPT, avec exceptions pour la gestion (8006, SSH, etc.) depuis le réseau local.

Comment s'écrit un identifiant d'utilisateur et d'un jeton d'API ?

joe@pve pour l'utilisateur ; joe@pve!monitoring pour le jeton.

Que compose une permission dans Proxmox ?

Un triplet chemin + sujet (utilisateur, groupe ou jeton) + rôle, avec propagation par défaut.

Quels rôles pour un accès en lecture seule et pour administrer des VM ?

PVEAuditor (lecture seule) et PVEVMAdmin (administration des VM).

Valeurs par défaut d'un pool Ceph et signification ?

size 3 (trois copies) et min_size 2 : les E/S continuent tant qu'au moins deux copies sont disponibles.

Quelle est la différence entre un volume thick et thin ?

Thick : tout l'espace est réservé à la création. Thin : les blocs sont alloués à l'écriture, ce qui permet de surallouer, avec le risque qu'un pool plein provoque des erreurs d'E/S sur tous les invités.

Pourquoi le LVM classique est-il déconseillé pour les snapshots, contrairement au LVM-thin ?

Un snapshot LVM classique ralentit toutes les écritures du groupe de volumes tant qu'il existe. Le LVM-thin gère snapshots et clones nativement et efficacement.

LVM-thin peut-il être partagé entre nœuds ?

Non, un pool thin est local à un nœud. Le LVM épais, lui, peut être partagé sur une LUN iSCSI/FC/SAS avec le drapeau shared.

Quand utiliser qcow2 plutôt que raw ?

Sur stockage fichier (répertoire, NFS, CIFS), pour avoir snapshots, thin provisioning et clones liés. raw est plus rapide mais sans fonctions. Sur LVM, ZFS ou Ceph, le volume est brut.

Quel est le défaut d'un snapshot interne qcow2 ?

Sa création ou suppression bloque la VM en marche et peut prendre très longtemps sur de gros disques, surtout sur NFS.

Qu'est-ce que « Snapshots as Volume-Chain » ?

Une fonction (aperçu technique depuis PVE 9.0) qui crée un volume par snapshot, chaînés en qcow2, par exemple sur LVM épais partagé. Efficace si le stockage dessous est thin avec discard.

Un snapshot VM remplace-t-il une sauvegarde ?

Non : il est sur le même stockage que le disque et se perd avec lui. Il sert de point de retour rapide avant une opération.

Quelle latence pour corosync et pourquoi un réseau dédié ?

Moins de 5 ms et stable ; au-delà de 10 ms, instable avec plus de 3 nœuds. La sensibilité est à la gigue : un lien saturé par stockage ou sauvegarde peut faire fencer des nœuds.

Que se passe-t-il à l'ajout d'un nœud au cluster ?

Authentification par le mot de passe root@pam d'un nœud et empreinte SHA-256 ; sa configuration /etc/pve est écrasée, il hérite des stockages et reçoit un certificat signé par la CA du cluster.

Dans quels cas un QDevice est-il recommandé ou déconseillé ?

Recommandé avec un nombre pair de nœuds (ajoute une voix). Déconseillé avec un nombre impair : le qnetd devient un point de défaillance unique.

Quelles sont les étapes pour retirer un nœud ?

Migrer ou supprimer les invités, sauvegarder, sortir des réplications et de Ceph, éteindre le nœud, pvecm delnode depuis un autre nœud, vérifier avec pvecm nodes, nettoyer /etc/pve/nodes/nœud.

Qu'est-ce qui est obligatoire quand on modifie corosync.conf ?

Travailler sur une copie, incrémenter config_version dans totem, garder une sauvegarde, puis remplacer le fichier.

Quelles sont les méthodes pour migrer une VM depuis VMware ?

Import automatique ESXi (assistant), live-import, OVF (qm importovf), import de disque (qm disk import), attach & move disk, restauration de sauvegarde, clonage direct.

Pourquoi éviter l'import via vCenter ?

Les performances sont fortement réduites ; il vaut mieux se connecter directement à l'hôte ESXi.

Que faut-il faire avant de migrer une VM Windows depuis VMware ?

Désinstaller VMware Tools, noter ou retirer l'IP statique, gérer la MAC (DHCP), éteindre la VM ; après import, démarrer en IDE/SATA puis installer les pilotes VirtIO avant de basculer.

Quelles sont les limites de l'import automatique ESXi ?

Pas de disques sur vSAN, import lent avec snapshots, pas de disques chiffrés, vTPM non migrable, datastores avec caractère spécial parfois en échec.

Quel danger avec la méthode attach & move disk ?

Allumer la VM des deux côtés (VMware et Proxmox) : corruption du disque. Éteindre la source avant de démarrer la cible.

Comment convertir un VMDK en qcow2 ?

qemu-img convert -p -f vmdk -O qcow2 Server.vmdk Server.qcow2, en pointant le fichier descripteur, avec le -flat.vmdk dans le même dossier ; puis qm disk import.

Quels formats sources autres que VMware peut-on importer ?

Hyper-V (vhd, vhdx), VirtualBox (vdi), Xen/KVM/OpenStack (qcow2, raw), OVA (à extraire), et machines physiques clonées en image brute.

Comment récupérer l'espace après passage en thin ?

Activer discard sur le disque de la VM puis fstrim (Linux) ou retrim (Windows) ; sans TRIM, remplir de zéros (zerofree, sdelete -z) puis reconvertir.

Quel est l'équivalent Proxmox d'un témoin de quorum Hyper-V ?

Le QDevice (corosync-qnetd sur un serveur externe indépendant).

Quel est l'équivalent des CSV et de Storage Spaces Direct ?

Un stockage partagé (NFS, Ceph, LVM sur SAN) pour les CSV, et Ceph (ou ZFS) pour Storage Spaces Direct.

Quel outil en ligne de commande donne un accès à l'API comme PowerShell ?

pvesh (par exemple pvesh get /cluster/resources --output-format json), avec qm et pct pour VM et conteneurs.

Quelles sont les phases d'un projet de migration VMware → Proxmox ?

Découverte et inventaire, conception cible, preuve de concept, pilote, vagues de migration, clôture avec décommissionnement.

Quand conserver la VM source après migration ?

Éteinte, non supprimée, jusqu'à validation par les métiers et fin de la période de rétention : c'est le plan de retour arrière.

Comment se calcule le quorum et pourquoi 2 nœuds sans QDevice sont fragiles ?

Quorum = ⌊votes/2⌋ + 1. Avec 2 nœuds il faut 2 votes : la moindre panne fait perdre le quorum. On ajoute un QDevice (3 votes) ou un troisième nœud.

Que se passe-t-il pour les VM quand le quorum est perdu ?

Les VM déjà démarrées continuent de tourner, mais /etc/pve passe en lecture seule : plus de démarrage d'invité ni de modification de config. Avec HA actif, les nœuds sans quorum se fencent au bout d'environ une minute.

Quel champ faut-il toujours incrémenter dans corosync.conf et pourquoi ?

config_version dans la section totem : sans incrément, la nouvelle configuration n'est pas propagée ni rechargée sur les nœuds.

Quelles commandes donnent l'état des liens et du quorum ?

pvecm status (votes, seuil, drapeau Quorate), corosync-cfgtool -s (état des liens), corosync-quorumtool -s et -l, journalctl -u corosync.

Quand utiliser pvecm expected 1 et quel est le risque ?

Pour retrouver le quorum sur un nœud survivant après la perte définitive des autres. Risque de split-brain si les autres nœuds sont en fait vivants : à vérifier avant.

Où placer le serveur QDevice ?

Sur une machine externe et indépendante du cluster, jamais sur une VM qu'il arbitre, joignable en TCP depuis chaque nœud.
