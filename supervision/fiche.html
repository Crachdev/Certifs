1Pourquoi superviser et quoi mesurerFondations
MétriquesLogsTracesSLO
Superviser, c'est savoir avant tes utilisateurs que quelque chose va mal, et avoir de quoi comprendre pourquoi. Analogie : le tableau de bord d'une voiture (témoins, jauges) plus la boîte noire pour comprendre un incident.

3Prometheus : le cœur de la collectePrometheus
ScrapeExportersPromQLTSDB
  • Pull : Prometheus vient chercher les métriques sur des cibles HTTP (/metrics) à intervalle régulier (scrape_interval)
  • Exporter : petit service qui expose les métriques d'un système (node_exporter pour Linux, windows_exporter, blackbox_exporter pour tester des URL)
  • Métrique = nom + labels + valeur (node_cpu_seconds_total{mode="idle",instance="srv1"})
  • Types : counter (monte seulement), gauge (monte et descend), histogram (répartition)
# prometheus.yml global: scrape_interval: 30s rule_files: - rules/*.yml alerting: alertmanagers: - static_configs: [ { targets: [ 'localhost:9093' ] } ] scrape_configs: - job_name: node static_configs: - targets: [ '10.0.0.61:9100', '10.0.0.62:9100' ] - job_name: web metrics_path: /probe params: { module: [ http_2xx ] } static_configs: [ { targets: [ 'https://monsite.fr' ] } ] relabel_configs: - source_labels: [ __address__ ] target_label: __param_target - target_label: __address__ replacement: localhost:9115 # blackbox_exporter

Requêtes PromQL utiles

# CPU utilisé (%) par machine 100 - (avg by (instance) (rate(node_cpu_seconds_total{mode="idle"}[5m])) * 100) # Mémoire disponible (%) node_memory_MemAvailable_bytes / node_memory_MemTotal_bytes * 100 # Disque : espace libre (%) hors systèmes temporaires node_filesystem_avail_bytes{fstype!~"tmpfs|overlay"} / node_filesystem_size_bytes * 100 # Cibles injoignables up == 0 # Disque plein dans 24 h (prévision linéaire sur 6 h) predict_linear(node_filesystem_avail_bytes[6h], 24*3600) < 0
Piège classique : un counter s'utilise avec rate(), jamais en valeur brute. Attention aussi aux labels à forte cardinalité (identifiant utilisateur, URL complète) qui font exploser la mémoire de Prometheus.
4Installer la pile en labo (Docker Compose)Prometheus
Docker ComposeGrafanaAlertmanagernode_exporter
# docker-compose.yml : Prometheus + Alertmanager + Grafana + node_exporter services: prometheus: image: prom/prometheus:latest # épingler une version en vrai volumes: - ./prometheus.yml:/etc/prometheus/prometheus.yml:ro - ./rules:/etc/prometheus/rules:ro - prom-data:/prometheus ports: [ "9090:9090" ] alertmanager: image: prom/alertmanager:latest volumes: [ "./alertmanager.yml:/etc/alertmanager/alertmanager.yml:ro" ] ports: [ "9093:9093" ] grafana: image: grafana/grafana:latest volumes: [ "grafana-data:/var/lib/grafana" ] ports: [ "3000:3000" ] node-exporter: image: prom/node-exporter:latest ports: [ "9100:9100" ] volumes: prom-data: {} grafana-data: {}
  1. docker compose up -d ; ouvrir :9090 (Prometheus, onglet Targets) et :3000 (Grafana)
  2. Dans Grafana : Connections → Data sources → Prometheus (http://prometheus:9090)
  3. Importer un tableau de bord communautaire pour Node Exporter (Dashboards → Import, identifier du catalogue grafana.com : à rechercher)
  4. Installer node_exporter sur chaque VM Linux (paquet de la distribution ou binaire + service systemd) et l'ajouter aux cibles
# Sur une VM Debian / Ubuntu sudo apt install prometheus-node-exporter systemctl status prometheus-node-exporter ; curl -s localhost:9100/metrics | head
En production : versions épinglées, stockage persistant et sauvegardé, authentification et TLS devant Grafana, accès restreint à Prometheus.

6Journaux centralisés : Loki et alternativesLogs
LokiAlloyrsyslogjournald
  • Pourquoi centraliser : ne plus se connecter machine par machine, conserver les journaux après la mort d'un conteneur ou d'une VM, corréler plusieurs sources
  • Loki n'indexe que les labels (pas le texte) : moins cher que Elastic ; on cherche avec LogQL
  • Agents de collecte : Promtail (historique), Grafana Alloy (successeur annoncé), Fluent Bit, Vector : vérifie l'état actuel de Promtail dans la documentation avant de le choisir
  • Linux : journald et rsyslog peuvent aussi envoyer vers un serveur central (@@serveur:514)
# LogQL : exemples (dans Grafana → Explore, source Loki) {job="varlogs"} |= "error" # lignes contenant error {namespace="monapp"} |~ "timeout|refused" # expression régulière sum by (pod) (rate({namespace="monapp"} |= "error" [5m])) # erreurs / seconde par pod
RègleDétail
Journaliser en texte structuré (JSON) quand c'est possiblePlus facile à filtrer
Ne jamais journaliser de secrets ni de données personnellesRGPD, sécurité
Définir une rétention (ex. 30 jours) et une rotationLe disque est fini
Horloge synchronisée (NTP)Corréler des événements entre machines

Alertes Kubernetes à prévoir

  • Nœud NotReady ; Pod en CrashLoopBackOff ou redémarrages répétés ; Pods Pending longtemps
  • Volume persistant presque plein ; certificats du control plane proches de l'expiration ; etcd lent ou sans leader
  • Dépassement de requests / limits, OOMKilled
  • Pour RKE2 : état des snapshots etcd (fraîcheur de la dernière sauvegarde)
Dans Rancher : Apps → Charts → Monitoring sur chaque cluster géré (voir Labo IaC, partie Rancher). Règle le stockage et la rétention pour ne pas remplir un disque.

11Plan de labo et Q/RPratique
Pratique18 questions

Plan de labo en 6 séances

  1. Séance 1 : lancer la pile (Compose) sur une VM, ajouter node_exporter sur 2 VM, voir les cibles UP
  2. Séance 2 : écrire 5 requêtes PromQL (CPU, RAM, disque, up, prévision de disque) et un premier tableau Grafana
  3. Séance 3 : 3 règles d'alerte + Alertmanager vers e-mail ou chat ; provoquer une panne et vérifier la réception
  4. Séance 4 : ajouter Proxmox (jeton PVEAuditor + exporter) et blackbox_exporter sur 2 sites, avec alerte d'expiration de certificat
  5. Séance 5 : installer Loki + collecteur, lire les journaux d'une VM et d'un Pod, requêtes LogQL
  6. Séance 6 : kube-prometheus-stack (ou Rancher Monitoring) sur le cluster RKE2 du Labo IaC, alertes Kubernetes, tableaux dans Git

Auto-évaluation — clique pour voir la réponse

Quels sont les trois piliers de l'observabilité ?

Métriques, journaux (logs) et traces.

Quels sont les 4 signaux dorés ?

Latence, trafic, erreurs et saturation.

Quelle différence entre SLI, SLO et SLA ?

SLI : l'indicateur mesuré ; SLO : l'objectif visé ; SLA : l'engagement contractuel.

Prometheus fonctionne-t-il en push ou en pull ?

En pull : il interroge périodiquement les endpoints /metrics des cibles.

À quoi sert un exporter ?

À exposer au format Prometheus les métriques d'un système qui n'en publie pas nativement (node_exporter, blackbox_exporter…).

Pourquoi utiliser rate() sur un counter ?

Un counter ne fait qu'augmenter ; rate() donne la variation par seconde, qui est la grandeur utile.

Que fait up == 0 ?

Sélectionne les cibles qui n'ont pas répondu au dernier scrape.

À quoi sert la clause for dans une règle d'alerte ?

À exiger que la condition dure un certain temps avant de déclencher, pour éviter les alertes sur des pics.

Quel est le rôle d'Alertmanager ?

Regrouper, dédupliquer, router et espacer les notifications d'alerte (e-mail, chat, astreinte).

Qu'est-ce que la fatigue d'alertes ?

Trop d'alertes inutiles : l'équipe finit par les ignorer, y compris les vraies.

Pourquoi alerter sur un symptôme plutôt que sur une cause ?

Parce qu'il reflète l'impact réel pour l'utilisateur et génère moins de faux positifs.

Quelle différence entre Prometheus et Loki ?

Prometheus stocke des métriques numériques ; Loki stocke des journaux indexés par labels.

Quel est le piège de la cardinalité ?

Des labels aux valeurs très nombreuses (identifiant, URL complète) multiplient les séries et saturent la mémoire de Prometheus.

Comment superviser Proxmox ?

Via le serveur de métriques intégré (InfluxDB / Graphite) ou prometheus-pve-exporter avec un jeton API en lecture seule.

Quel est le rôle de kube-state-metrics ?

Exposer l'état des objets Kubernetes (Pods, Deployments, nœuds) sous forme de métriques.

Quelle différence entre metrics-server et Prometheus ?

metrics-server fournit CPU / mémoire pour kubectl top et l'HPA, sans historique ; Prometheus conserve l'historique et alimente les alertes.

Qui supervise le superviseur ?

Un contrôle externe ou un « dead man's switch » : une alerte permanente dont l'absence signale la panne de la supervision.

Pourquoi suivre la fraîcheur de la dernière sauvegarde ?

Une sauvegarde qui échoue en silence est une panne future : c'est une métrique de santé essentielle.
