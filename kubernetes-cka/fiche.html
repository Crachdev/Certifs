Architecture · 25 %

Architecture, Installation & Configuration

Composants du control plane, kubeadm, RBAC, Helm, opérateurs

Composants du cluster

kube-apiserver

Point d'entrée unique de toutes les requêtes. Authentifie, autorise (RBAC), valide et persiste dans etcd. Stateless — peut être répliqué.

etcd

Base de données clé-valeur distribuée (Raft). Stocke tout l'état du cluster. Sauvegarder avec etcdctl snapshot save.

kube-scheduler

Assigne les Pods aux nœuds selon resources, affinity, taints/tolerations. Ne démarre pas les containers — délègue au kubelet.

kube-controller-manager

Exécute les boucles de contrôle : Node Controller, ReplicaSet Controller, Endpoints Controller, etc.

kubelet

Agent sur chaque nœud. Reçoit les PodSpecs (via apiserver), crée les containers via le CRI, envoie le statut au plan de contrôle.

kube-proxy

Maintient les règles réseau (iptables ou IPVS) pour le routage des Services. Ne touche pas le trafic pod-à-pod direct.

Installer un cluster avec kubeadm

# Sur tous les nœuds — désactiver le swap
swapoff -a && sed -i '/swap/d' /etc/fstab

# Initialiser le control plane
kubeadm init \
  --pod-network-cidr=192.168.0.0/16 \
  --apiserver-advertise-address=192.168.1.10

# Configurer kubectl (en tant qu'utilisateur normal)
mkdir -p $HOME/.kube
cp /etc/kubernetes/admin.conf $HOME/.kube/config

# Installer un CNI (ex: Calico)
kubectl apply -f https://raw.githubusercontent.com/projectcalico/calico/v3.28.0/manifests/calico.yaml

# Rejoindre un worker node (commande donnée par kubeadm init)
kubeadm join 192.168.1.10:6443 \
  --token abcdef.0123456789abcdef \
  --discovery-token-ca-cert-hash sha256:...

CRD & Opérateurs

CRD — Custom Resource Definition

Étend l'API Kubernetes avec de nouveaux types de ressources. Exemple : kind: Certificate pour cert-manager.

Opérateur

Controller custom qui utilise des CRD pour automatiser la gestion d'applications complexes (databases, kafka…). Installe via Helm ou OLM.

Haute disponibilité du control plane

Un cluster HA nécessite 3 ou 5 nœuds control plane (nombre impair pour le quorum etcd). kubeadm supporte le mode HA via --control-plane-endpoint pointant vers un load balancer (HAProxy, cloud LB). Les nœuds workers rejoignent comme d'habitude.
Workloads & Scheduling · 15 %

Workloads & Scheduling

Deployments, ConfigMaps/Secrets, autoscaling, affinités

Types de workloads

Deployment

Gère des Pods stateless avec rolling updates. Supporte rollback, pause/resume. Utilise un ReplicaSet sous-jacent.

StatefulSet

Pods avec identité stable (nom-0, nom-1…) et stockage persistant ordonnancé. Pour databases, Kafka, Elasticsearch.

DaemonSet

Un Pod par nœud (ou sélection). Utilisé pour agents de monitoring (Prometheus node-exporter), CNI plugins, log shippers.

Job / CronJob

Job : exécution ponctuelle jusqu'à complétion. CronJob : planification cron. completions, parallelism, backoffLimit.

Rolling update & rollback

# Mettre à jour l'image d'un deployment
kubectl set image deployment/nginx-deploy nginx=nginx:1.25

# Surveiller le rollout
kubectl rollout status deployment/nginx-deploy

# Historique des révisions
kubectl rollout history deployment/nginx-deploy

# Rollback à la révision précédente
kubectl rollout undo deployment/nginx-deploy

# Rollback à une révision précise
kubectl rollout undo deployment/nginx-deploy --to-revision=2

ConfigMap & Secret

# Créer un ConfigMap depuis des valeurs
kubectl create configmap app-config \
  --from-literal=DB_HOST=postgres \
  --from-literal=DB_PORT=5432

# Créer un Secret opaque
kubectl create secret generic db-secret \
  --from-literal=password=s3cr3t

# Consommer via envFrom dans un Pod
# spec.containers[].envFrom:
#   - configMapRef: { name: app-config }
#   - secretRef:    { name: db-secret  }

Scheduling avancé

# Taint un nœud (empêche les Pods sans tolérance)
kubectl taint nodes node1 key=gpu:NoSchedule

# Tolérance dans le Pod spec
# tolerations:
# - key: "gpu" operator: "Equal" value: "gpu" effect: "NoSchedule"

# Node affinity (préférence)
# affinity.nodeAffinity.preferredDuringSchedulingIgnoredDuringExecution

# Forcer un nœud avec nodeName (bypass scheduler)
# spec.nodeName: node1

Limites & Requests

⚠️ Un Pod sans requests peut être évincé en premier lors d'une pression mémoire (QoS BestEffort). Toujours définir requests et limits en prod. Requests = réservation nœud. Limits = plafond hard (OOMKill si dépassé pour mémoire).

Ingress

Ingress Controller

Composant qui lit les objets Ingress et configure un reverse proxy (nginx, Traefik, HAProxy). Doit être déployé séparément (n'est pas inclus par défaut).

Ingress Resource

Règles HTTP(S) : routing par hostname et path vers des Services. Supporte TLS via Secret de type kubernetes.io/tls.

# Exemple d'Ingress avec TLS
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: web-ingress
  annotations:
    nginx.ingress.kubernetes.io/rewrite-target: /
spec:
  tls:
  - hosts: [app.example.com]
    secretName: tls-secret
  rules:
  - host: app.example.com
    http:
      paths:
      - path: /api
        pathType: Prefix
        backend:
          service: { name: api-svc, port: { number: 80 } }

NetworkPolicy

⚠️ Les NetworkPolicies nécessitent un CNI qui les supporte (Calico, Cilium, Weave). Par défaut, tout trafic est autorisé. Une NetworkPolicy vide sur un Pod bloque tout le trafic non explicitement autorisé. 
# Autoriser uniquement le trafic entrant depuis le namespace "frontend"
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-from-frontend
spec:
  podSelector:
    matchLabels: { app: backend }
  policyTypes: [Ingress]
  ingress:
  - from:
    - namespaceSelector:
        matchLabels: { name: frontend }

CoreDNS

  • DNS interne du cluster, déployé comme Deployment dans kube-system
  • Format FQDN : <svc>.<ns>.svc.cluster.local / <pod-ip>.<ns>.pod.cluster.local
  • Config dans le ConfigMap coredns (espace kube-system)
  • Dépanner : kubectl exec -it <pod> -- nslookup kubernetes.default

Gateway API (nouveau)

La Gateway API remplace progressivement Ingress avec un modèle plus expressif : GatewayClass (infrastructure), Gateway (listener), HTTPRoute / TCPRoute (règles). Supporte le routage par header, poids, etc.
Storage · 10 %

Storage

PV, PVC, StorageClass, modes d'accès, reclaim policies

Architecture du stockage

PersistentVolume (PV)

Ressource de stockage provisionnée par l'admin (ou dynamiquement). Indépendant du cycle de vie des Pods.

PersistentVolumeClaim (PVC)

Demande de stockage par un Pod. Le scheduler trouve le PV correspondant (capacity, accessMode, storageClass).

StorageClass

Définit le provisioner et les paramètres pour le provisionnement dynamique. Évite de créer des PV manuellement.

CSI Driver

Plugin standard pour intégrer n'importe quel système de stockage (EBS, GCE PD, NFS, Ceph…) sans modifier K8s.

Access Modes

ModeAbrév.Description
ReadWriteOnceRWOUn seul nœud peut monter en lecture/écriture
ReadOnlyManyROXPlusieurs nœuds peuvent monter en lecture seule
ReadWriteManyRWXPlusieurs nœuds en lecture/écriture (NFS, CephFS…)
ReadWriteOncePodRWOPUn seul Pod en lecture/écriture (K8s 1.22+)

Reclaim Policies

PolicyComportement quand le PVC est supprimé
RetainPV conservé, données préservées, doit être libéré manuellement
DeletePV et données supprimés automatiquement (défaut cloud)
RecycleDéprecié — rm -rf + re-mise à disposition
# Créer un PVC et le monter dans un Pod
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: data-pvc
spec:
  accessModes: [ReadWriteOnce]
  storageClassName: standard
  resources:
    requests:
      storage: 5Gi
---
# Dans le Pod spec:
# volumes:
#   - name: data
#     persistentVolumeClaim: { claimName: data-pvc }
# containers[].volumeMounts:
#   - name: data  mountPath: /var/data
Troubleshooting · 30 %

Troubleshooting — le domaine le plus lourd

Clusters, composants, networking, logging — maîtriser ce domaine = réussir le CKA

Méthodologie de diagnostic

🔍 Toujours dans cet ordre : 1. describe la ressource → 2. logs du container → 3. events du namespace → 4. composants système (kubelet, apiserver) → 5. réseau

Dépannage des Pods

# Voir les events et l'état d'un Pod
kubectl describe pod <pod-name>

# Logs du container en cours
kubectl logs <pod-name> -c <container> --previous

# Shell interactif dans un Pod
kubectl exec -it <pod-name> -- /bin/sh

# Pod de debug éphémère (K8s 1.23+)
kubectl debug -it <pod-name> --image=busybox --target=<container>

États des Pods — signification

ÉtatCause probableAction
PendingPas assez de ressources, PVC en attente, nœud taintédescribe pod → Events
CrashLoopBackOffContainer crash au démarrage répétélogs --previous
ImagePullBackOffImage introuvable ou registry inaccessibleVérifier nom/tag, imagePullSecrets
OOMKilledMémoire limits dépasséeAugmenter limits ou corriger memory leak
ContainerCreatingVolume non monté, ConfigMap/Secret manquantdescribe pod → Events
NodeNotReadykubelet HS, réseau CNI, disque pleinsystemctl status kubelet

Dépannage des nœuds

# Status et conditions des nœuds
kubectl get nodes
kubectl describe node <node-name>

# Logs du kubelet (sur le nœud directement)
systemctl status kubelet
journalctl -u kubelet -n 100

# Vérifier les static Pods du control plane
ls /etc/kubernetes/manifests/

# Redémarrer le kubelet
systemctl daemon-reload && systemctl restart kubelet

Dépannage des Services et du réseau

# Vérifier les endpoints d'un Service
kubectl get endpoints <service-name>
# → si vide : les labels du selector ne matchent aucun Pod

# Tester la connectivité depuis un Pod
kubectl run test --image=busybox --rm -it -- wget -O- http://<service>:80

# Vérifier kube-proxy
kubectl get ds kube-proxy -n kube-system
iptables -t nat -L KUBE-SERVICES | grep <service-ip>

Sauvegarde & restauration etcd

# Snapshot etcd
ETCDCTL_API=3 etcdctl snapshot save /backup/etcd-snapshot.db \
  --endpoints=https://127.0.0.1:2379 \
  --cacert=/etc/kubernetes/pki/etcd/ca.crt \
  --cert=/etc/kubernetes/pki/etcd/server.crt \
  --key=/etc/kubernetes/pki/etcd/server.key

# Vérifier le snapshot
ETCDCTL_API=3 etcdctl snapshot status /backup/etcd-snapshot.db

# Restauration
ETCDCTL_API=3 etcdctl snapshot restore /backup/etcd-snapshot.db \
  --data-dir=/var/lib/etcd-restore

RBAC · Sécurité

RBAC — Role Based Access Control

Roles, ClusterRoles, RoleBindings — composant central du CKA

Role

Permissions dans un namespace précis. Exemple : lire les Pods dans default.

ClusterRole

Permissions cluster-wide (nœuds, PV, namespaces) ou réutilisable dans plusieurs namespaces.

RoleBinding

Lie un Role (ou ClusterRole) à un user/group/SA dans un namespace.

ClusterRoleBinding

Lie un ClusterRole à un subject pour tout le cluster.

# Créer un Role qui permet de lire les pods
kubectl create role pod-reader \
  --verb=get,list,watch \
  --resource=pods

# Lier ce Role à un utilisateur
kubectl create rolebinding bob-pod-reader \
  --role=pod-reader \
  --user=bob

# ClusterRole pour accéder aux nœuds
kubectl create clusterrole node-reader \
  --verb=get,list \
  --resource=nodes

# Vérifier les permissions d'un utilisateur
kubectl auth can-i create pods --as=bob
kubectl auth can-i get nodes --as=system:serviceaccount:default:my-sa
⚠️ Service Account ≠ User. Les Pods utilisent des ServiceAccounts pour s'authentifier à l'API. Par défaut, le SA default de chaque namespace a des permissions minimales. Toujours créer des SA dédiés en prod et lier uniquement les permissions nécessaires.
⚠️ Pièges & astuces

Pièges courants à l'examen CKA

Erreurs classiques qui font perdre des points

Oublier le contexte

Chaque tâche CKA spécifie un contexte et/ou un namespace. Toujours lancer kubectl config use-context <ctx> avant de commencer.

Ne pas lire le namespace

Beaucoup de ressources sont dans un namespace précis. Vérifier avec -n <ns> ou -A. Un Pod "introuvable" est souvent dans un autre namespace.

Certificats etcd

Toujours passer les 3 flags TLS à etcdctl : --cacert, --cert, --key. Sans ça, la commande échoue silencieusement.

Static Pods vs Deployments

Les composants du control plane (apiserver, etcd…) sont des Static Pods dans /etc/kubernetes/manifests/. Ne pas essayer de les gérer avec kubectl delete pod.

Selector labels

Un Service n'a pas d'Endpoints ? Vérifier que ses labels spec.selector matchent exactement les labels des Pods (casse, tirets, etc.).

imagePullPolicy

Avec :latest, imagePullPolicy est Always par défaut. En examen, utiliser des tags précis pour éviter les pulls réseau.

PVC en Pending

Un PVC reste Pending si aucun PV compatible n'existe (accessMode, storageClass, capacity). Vérifier avec kubectl describe pvc.

Permissions RBAC manquantes

Un Pod qui échoue à appeler l'API K8s : vérifier le ServiceAccount, le Role et le RoleBinding. Tester avec kubectl auth can-i.

NetworkPolicy bloque tout

Une NetworkPolicy avec un podSelector vide {} s'applique à tous les Pods du namespace. Toujours limiter avec des labels précis.

Kubelet pas redémarré

Après modification d'un fichier de config kubelet ou manifest Static Pod, faire systemctl daemon-reload && systemctl restart kubelet pour appliquer.

Routine de préparation d'une tâche CKA

# 1. Changer de contexte (toujours !)
kubectl config use-context <context-donné>

# 2. Vérifier le namespace de la tâche
export NS=<namespace>

# 3. Lire la ressource existante si besoin
kubectl get <resource> -n $NS

# 4. Générer le YAML de base
kubectl create <resource> <name> ... --dry-run=client -o yaml > /tmp/task.yaml

# 5. Éditer si nécessaire
vi /tmp/task.yaml

# 6. Appliquer
kubectl apply -f /tmp/task.yaml

# 7. Vérifier
kubectl get <resource> -n $NS
kubectl describe <resource> <name> -n $NS
