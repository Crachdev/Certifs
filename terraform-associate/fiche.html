IaC Concepts — 7%

IaC

Infrastructure as Code

L'IaC permet de provisionner et gérer l'infrastructure via des fichiers de configuration versionnables. Avantages : idempotence, reproductibilité, auditabilité, collaboration.

Approches IaC

Déclarative (Terraform, CloudFormation) : on décrit l'état désiré, l'outil trouve le chemin.
Impérative (scripts Bash, Ansible) : on décrit les étapes à exécuter.

Idempotence

Appliquer la même configuration plusieurs fois produit toujours le même résultat. Terraform compare l'état actuel au desired state avant d'agir.

Mutable vs Immutable

Mutable : on modifie les ressources existantes (Ansible). Immutable : on recrée les ressources à chaque changement (Terraform recommande ce pattern via create_before_destroy).

Purpose of Terraform — 8%

Cloud

Multi-cloud & Provider agnostic

Terraform gère AWS, Azure, GCP, Kubernetes, et +3000 providers via le Terraform Registry. Un seul outil, tous les clouds.

HashiCorp Configuration Language

HCL est lisible par l'humain et par la machine. Syntaxe JSON aussi supportée. Les fichiers .tf contiennent resources, variables, outputs, providers.

Terraform vs Outils similaires

vs Ansible : Terraform = provisioning IaC, Ansible = configuration management.
vs CloudFormation : CFN = AWS only, Terraform = multi-cloud.
vs Pulumi : langage général vs HCL.

Terraform Registry

Dépôt officiel de providers et modules : registry.terraform.io. Les providers officiels (AWS, Azure, GCP) sont maintenus par HashiCorp ou les cloud vendors.

✓ Terraform Open Source vs Enterprise Terraform CLI = open source (MPL 2.0). Terraform Cloud = SaaS avec workspace remote, collaboration. Terraform Enterprise = version auto-hébergée pour grandes entreprises.

Terraform Basics — 24%

IaC

Blocs fondamentaux

terraform block

Configure le comportement de Terraform lui-même : version requise, providers requis, backend.

  • required_version
  • required_providers
  • backend
  • cloud (Terraform Cloud)

provider block

Configure un provider spécifique. Plusieurs instances possibles via alias. Les credentials proviennent de variables env ou fichiers de config.

  • provider "aws" { region = "..." }
  • Alias multi-région
  • version constraints

resource block

Déclare une ressource d'infrastructure. Syntaxe : resource "type" "nom_local" { ... }. Référence : type.nom.attribut.

  • depends_on
  • count / for_each
  • lifecycle
  • provisioner

data block

Lit des données existantes depuis un provider sans les gérer. Utile pour référencer des ressources créées hors Terraform.

  • data "aws_ami" "ubuntu" { ... }
  • Référence : data.type.nom.attribut
  • Lecture seule, jamais modifié

Variables

variable block

Paramétrise la configuration. Types : string, number, bool, list, map, object, tuple, set.

  • default (optionnel)
  • description
  • type constraint
  • sensitive = true
  • validation blocks

Priorité des variables

Ordre croissant de priorité :

  • 1. default dans le bloc variable
  • 2. Fichier terraform.tfvars
  • 3. Fichiers *.auto.tfvars
  • 4. Option -var-file
  • 5. Option -var
  • 6. Variables d'env TF_VAR_*

locals block

Définit des expressions réutilisables localement. Ne sont pas configurables depuis l'extérieur (contrairement aux variables).

locals {
  common_tags = {
    env  = var.env
    team = "platform"
  }
}

output block

Expose des valeurs après apply. Utilisé pour passer des infos entre modules ou afficher des résultats.

  • value (requis)
  • description
  • sensitive = true
  • depends_on

Expressions & Fonctions

# Expressions courantes
# count
resource "aws_instance" "web" {
  count = 3
  ami   = "ami-0abc123"
  tags = {
    Name = "web-${count.index}"
  }
}

# for_each (préféré à count pour des maps)
resource "aws_s3_bucket" "buckets" {
  for_each = toset(["logs", "data", "backup"])
  bucket   = "myapp-${each.key}"
}

# Expressions conditionnelles
instance_type = var.env == "prod" ? "t3.large" : "t3.micro"

# Fonctions utiles
length(var.subnets)        # nombre d'éléments
toset(var.list)            # convertit liste en set
tomap({a=1})               # convertit en map
lookup(map, key, default)  # lookup dans une map
merge(map1, map2)          # fusionne des maps
flatten(list_of_lists)     # aplatit des listes
file("./script.sh")        # lit un fichier
templatefile("tpl", vars) # template avec variables
jsonencode(object)         # encode en JSON
base64encode(string)       # encode en base64
cidrsubnet("10.0.0.0/16", 8, 1) # calcule un sous-réseau

Lifecycle meta-arguments

create_before_destroy

Crée la nouvelle ressource avant de détruire l'ancienne. Évite les interruptions lors des remplacements. Essentiel pour les ressources sans downtime.

prevent_destroy

Empêche la destruction de la ressource via terraform destroy ou lors d'un plan qui détruirait la ressource. Protège les ressources critiques (bases de données).

ignore_changes

Ignore les changements sur certains attributs. Utile pour des attributs gérés en dehors de Terraform (ex: tags ajoutés manuellement).

lifecycle {
  ignore_changes = [tags]
}

replace_triggered_by

Remplace la ressource si une autre ressource ou attribut change. Depuis Terraform 1.2.

lifecycle {
  replace_triggered_by = [
    aws_instance.web
  ]
}

Provisioners

⚠ Utilisation déconseillée Les provisioners sont un dernier recours. Préférer des outils dédiés (Ansible, cloud-init, user_data). Ils rendent les configurations fragiles et non idempotentes.

local-exec

Exécute une commande sur la machine qui lance Terraform (pas sur la ressource créée).

provisioner "local-exec" {
  command = "ansible-playbook ..."
}

remote-exec

Se connecte en SSH/WinRM à la ressource et exécute des commandes. Nécessite connection block.

file

Copie des fichiers ou répertoires locaux vers la ressource créée. Nécessite connection block.

null_resource

Ressource virtuelle sans infra réelle. Utile pour exécuter des provisioners liés à d'autres ressources via triggers.

Terraform CLI — 16%

CLI

Commandes principales

# === Workflow principal ===
terraform init          # initialise, télécharge providers + modules
terraform validate      # valide la syntaxe HCL
terraform fmt           # formate les fichiers .tf
terraform plan          # aperçu des changements (dry run)
terraform apply         # applique les changements
terraform destroy       # détruit toutes les ressources gérées

# === Flags importants ===
terraform plan -out=tfplan      # sauvegarde le plan
terraform apply tfplan          # applique le plan sauvegardé
terraform apply -auto-approve   # sans confirmation (CI/CD)
terraform plan -var="env=prod"  # passe une variable
terraform plan -target=aws_instance.web # cible une ressource
terraform plan -refresh=false   # ne rafraîchit pas le state

# === State ===
terraform state list              # liste les ressources dans le state
terraform state show aws_instance.web # détails d'une ressource
terraform state mv old.name new.name  # renomme sans recréer
terraform state rm aws_instance.web   # retire du state (sans détruire)
terraform state pull              # télécharge le state distant
terraform state push terraform.tfstate # pousse le state

# === Import ===
terraform import aws_instance.web i-1234567890 # importe une ressource existante
# Depuis Terraform 1.5 : bloc import{} dans la config

# === Inspection ===
terraform output                  # affiche les outputs
terraform output instance_ip      # output spécifique
terraform output -json            # format JSON
terraform show                    # affiche le state actuel
terraform show tfplan              # affiche un plan sauvegardé
terraform graph                   # graphe des dépendances (DOT)

# === Workspaces ===
terraform workspace list
terraform workspace new staging
terraform workspace select prod
terraform workspace show
terraform workspace delete staging

# === Autres ===
terraform console                 # REPL pour évaluer des expressions
terraform taint aws_instance.web  # marque pour recréation (deprecated → use -replace)
terraform apply -replace=aws_instance.web # remplace une ressource
terraform providers               # liste les providers requis
terraform providers lock          # crée/met à jour .terraform.lock.hcl
terraform force-unlock LOCK_ID    # déverrouille le state manuellement
✓ terraform init en détail terraform init télécharge les providers dans .terraform/providers/, initialise le backend, et installe les modules. Le fichier .terraform.lock.hcl verrouille les versions des providers. À commiter dans Git.

Terraform Modules — 12%

Modules

Root Module

Le répertoire courant où Terraform est invoqué. Contient la configuration principale. Tous les fichiers .tf du répertoire courant forment le root module.

Child Module

Module appelé depuis un autre module via un bloc module. Peut provenir du système de fichiers local, du Registry Terraform ou d'un dépôt Git.

Module Sources

  • Local : ./modules/vpc
  • Registry : hashicorp/consul/aws
  • GitHub : github.com/org/repo
  • Git : git::https://...
  • S3 : s3::https://...

Module Versioning

Contraintes de version via version = "~> 3.0". ~> 3.0 = ≥ 3.0 et < 4.0. ~> 3.1.0 = ≥ 3.1.0 et < 3.2.0. Uniquement pour les modules du Registry.

# Appel d'un module
module "vpc" {
  source  = "terraform-aws-modules/vpc/aws"
  version = "~> 5.0"

  name = "my-vpc"
  cidr = "10.0.0.0/16"

  azs             = ["eu-west-1a", "eu-west-1b"]
  private_subnets = ["10.0.1.0/24", "10.0.2.0/24"]
  public_subnets  = ["10.0.101.0/24", "10.0.102.0/24"]
}

# Accès aux outputs du module
vpc_id = module.vpc.vpc_id

# Structure recommandée d'un module
# modules/my-module/
#   main.tf       — ressources principales
#   variables.tf  — inputs
#   outputs.tf    — outputs
#   versions.tf   — required_providers
#   README.md     — documentation
✓ Bonnes pratiques modules Un module doit avoir des variables.tf, outputs.tf et versions.tf séparés. Pas de configuration de provider dans les modules enfants (ils héritent du root). Utiliser terraform init après chaque ajout/modification de module.

Core Workflow — 11%

Workflow

Write → Plan → Apply

Le workflow de base : Write (écrire la config HCL), Plan (vérifier les changements prévus), Apply (appliquer). Toujours relire le plan avant d'appliquer.

terraform plan

Génère un plan d'exécution. Symboles :
+ création
- destruction
~ modification in-place
-/+ destroy + create (replacement)

Refresh

Par défaut, plan/apply rafraîchissent le state depuis l'API du provider. -refresh=false désactive ce comportement pour accélérer. terraform refresh est deprecated → utiliser terraform apply -refresh-only.

Drift Detection

terraform apply -refresh-only détecte les changements fait hors Terraform (drift) et propose de mettre à jour le state sans modifier l'infra.

✓ terraform plan -out et apply Sauvegarder le plan avec -out=tfplan garantit que l'apply exécute exactement ce qui a été approuvé, sans surprise si la config a changé entre les deux commandes. Pratique recommandée en CI/CD.

Dépendances

Dépendances implicites

Terraform détecte automatiquement les dépendances via les références entre ressources. Si ressource B référence un attribut de ressource A, A sera créée en premier.

depends_on

Dépendance explicite pour les cas où les références ne suffisent pas (ex: politiques IAM qui doivent exister avant la ressource). À utiliser avec parcimonie.

State Management — 16%

State

terraform.tfstate

Rôle du State

Terraform stocke les mappings entre ressources HCL et ressources réelles dans le terraform.tfstate (JSON). C'est la source de vérité pour ce que Terraform gère.

State Locking

Prévient les opérations concurrentes qui corromprait le state. Supporté par S3+DynamoDB, Terraform Cloud, GCS, etc. Local state = pas de locking.

Sensitive Data

Le state peut contenir des données sensibles en clair (mots de passe, clés). Chiffrer le backend (S3 avec SSE, Terraform Cloud). Ne jamais commiter le state dans Git.

State Versioning

Activer le versioning S3 sur le bucket qui stocke le state pour permettre les rollbacks. Terraform Cloud conserve l'historique automatiquement.

Remote Backends

# Backend S3 (le plus courant pour AWS)
terraform {
  backend "s3" {
    bucket         = "my-terraform-state"
    key            = "prod/terraform.tfstate"
    region         = "eu-west-1"
    encrypt        = true
    dynamodb_table = "terraform-lock"  # table avec LockID (string)
  }
}

# Backend Terraform Cloud
terraform {
  cloud {
    organization = "my-org"
    workspaces {
      name = "my-workspace"
    }
  }
}

# Partial configuration (credentials en dehors du code)
terraform {
  backend "s3" {}  # vide
}

# terraform init -backend-config=backend.hcl

Workspaces

Concept

Les workspaces permettent d'avoir plusieurs states indépendants dans le même backend pour la même configuration. Utile pour dev/staging/prod avec la même config.

  • Workspace par défaut : default
  • Variable : terraform.workspace

Usage

resource "aws_instance" "web" {
  instance_type = (
    terraform.workspace == "prod"
    ? "t3.large"
    : "t3.micro"
  )
}

Limitations

Les workspaces partagent la même configuration HCL. Pour des environnements vraiment différents, considérer des répertoires séparés ou terragrunt.

State dans S3

Avec le backend S3, les workspaces stockent les states dans : env:/WORKSPACE_NAME/KEY. Le workspace default reste à la racine KEY.

Configuration avancée — 6%

IaC

Dynamic Blocks

# Génère des blocs répétitifs dynamiquement
resource "aws_security_group" "sg" {
  name = "web-sg"

  dynamic "ingress" {
    for_each = var.ingress_rules
    content {
      from_port   = ingress.value.from_port
      to_port     = ingress.value.to_port
      protocol    = ingress.value.protocol
      cidr_blocks = ingress.value.cidr_blocks
    }
  }
}

moved block (Terraform 1.1+)

# Renommer une ressource sans la détruire/recréer
moved {
  from = aws_instance.web
  to   = aws_instance.app_server
}

# Équivaut à terraform state mv, mais déclaratif

check block (Terraform 1.5+)

# Validation post-apply via assertions
check "health_check" {
  data "http" "endpoint" {
    url = "https://${aws_lb.web.dns_name}/health"
  }

  assert {
    condition     = data.http.endpoint.status_code == 200
    error_message = "Health check failed!"
  }
}

Expressions for

# for expression (liste)
[for s in var.list : upper(s)]

# for expression (map)
{for k, v in var.map : k => upper(v)}

# avec filtre
[for s in var.list : s if s != ""]

Splat Expressions

# Legacy splat
aws_instance.web.*.id

# Full splat (préféré)
aws_instance.web[*].id

# Accès à attributs imbriqués
var.users[*].name

Sensitive Variables

Marquer une variable sensitive = true masque sa valeur dans les logs/plan. Les outputs qui référencent des valeurs sensibles doivent aussi être marqués sensitive = true.

precondition / postcondition

lifecycle {
  precondition {
    condition = var.env != "prod" || var.instance_type == "t3.large"
    error_message = "Prod needs t3.large"
  }
}

Terraform Cloud & Enterprise

Cloud

Workspaces Terraform Cloud

Unité de déploiement dans TFC. Contient : state, variables, historique des runs. Différent des workspaces CLI — chaque workspace TFC a son propre state.

Remote Operations

Les plans et apply s'exécutent sur les runners de Terraform Cloud. Logs centralisés, notifications, approbations. Les credentials sont stockés dans TFC, pas en local.

Sentinel

Framework de policy-as-code d'HashiCorp (Terraform Enterprise/Cloud). Permet d'écrire des politiques pour valider/bloquer des configurations avant apply. Ex: interdire des instances coûteuses.

Private Registry

Terraform Cloud héberge un registry privé pour partager modules et providers en interne. Supporte le versioning et la documentation automatique depuis README.

Pièges & erreurs fréquentes

Exam

🚫 count vs for_each

count crée des ressources indexées par numéro. Si on supprime un élément du milieu, Terraform recrée toutes les suivantes. Préférer for_each avec des maps/sets pour éviter les destructions non désirées.

🚫 Ne pas versionner le state

Ne jamais stocker terraform.tfstate dans Git. Il contient des secrets en clair et les conflits de merge corrompent le state. Utiliser un remote backend.

🚫 terraform taint (deprecated)

terraform taint est déprécié depuis 0.15.2. Utiliser terraform apply -replace=resource.name à la place.

🚫 provider dans les modules enfants

Ne pas configurer de provider dans les modules enfants (sauf alias explicite). Les modules héritent de la configuration du root module. Passer les providers explicitement si nécessaire.

🚫 terraform refresh (deprecated)

terraform refresh est déprécié. Utiliser terraform apply -refresh-only pour détecter le drift et mettre à jour le state sans modifier l'infra.

🚫 Modifier le state manuellement

Ne jamais éditer directement terraform.tfstate à la main. Utiliser les commandes terraform state mv, terraform state rm, terraform import.

🚫 Contraintes de version trop souples

version = ">= 1.0" peut provoquer des mises à jour non désirées. Utiliser ~> (pessimistic constraint) : ~> 1.2 = ≥1.2 et <2.0.

🚫 Lock file absent

.terraform.lock.hcl doit être committé dans Git. Il verrouille les versions exactes des providers pour garantir la reproductibilité entre membres de l'équipe.

🚫 Sensitive outputs non marqués

Si un output référence une variable sensitive, il faut aussi marquer l'output sensitive = true. Sinon Terraform lèvera une erreur.

🚫 terraform destroy en prod

Protéger avec prevent_destroy = true dans le lifecycle. En CI/CD, ne jamais donner accès à terraform destroy sans double validation humaine.
