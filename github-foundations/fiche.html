02

Introduction à Git et GitHub

📘 Domain 1 · 22%

Git — concepts fondamentaux

Dépôt (Repository)Projet Git contenant tous les fichiers + historique complet. Local (.git/) ou distant (GitHub).
CommitInstantané (snapshot) de l'état du projet à un moment T. Chaque commit a un SHA unique.
Branche (Branch)Pointeur vers un commit. Permet de travailler en isolation. main est la branche principale par convention.
MergeFusionner une branche dans une autre. Crée un merge commit (fast-forward si possible).
CloneCopier un dépôt distant en local. git clone <url> — inclut tout l'historique.
ForkCopier un dépôt sur son compte GitHub. Indépendant de l'original. Pour contribuer sans accès direct.
Staging AreaZone intermédiaire entre les modifications et le commit. git add met en staging.

Flux de travail Git

Workflow standard git status → git add . → git commit -m "message" → git push origin main

GitHub — spécificités

GitHub vs GitGit = outil de versioning local. GitHub = plateforme hébergeant des repos Git + outils de collaboration (PRs, Issues, Actions…).
README.mdFichier affiché en page d'accueil d'un repo. Format Markdown. Décrit le projet, l'installation, l'utilisation.
GistMini-dépôt GitHub pour partager des snippets de code ou notes. Public ou secret.
GitHub CLIOutil gh pour interagir avec GitHub depuis le terminal. PRs, Issues, repos via CLI.

Authentification GitHub

HTTPS + Token

  • PAT (Personal Access Token)
  • Scope : granulaire (repos, actions…)
  • Fine-grained PATs (recommandé)

SSH

  • Clé publique/privée
  • Plus sécurisé que HTTPS
  • ssh-keygen + ajouter dans Settings

GitHub CLI / OAuth

  • gh auth login
  • OAuth App ou GitHub App
  • Token stocké sécurisé
03

Fonctionnalités de collaboration

🤝 Domain 2 · 30%

Pull Requests (PRs)

Pull RequestDemande de fusion d'une branche vers une autre. Inclut la revue de code, les commentaires, les modifications.
Merge optionsMerge commit : conserve l'historique complet | Squash & merge : un seul commit | Rebase : historique linéaire.
Draft PRPR en cours de développement, pas encore prête pour revue. Signale le travail sans demander une revue formelle.
CODEOWNERSFichier .github/CODEOWNERS définissant qui doit approuver les modifications de certains fichiers.
Required reviewersRevues obligatoires avant merge. Configuré dans les Branch Protection Rules.

Issues

IssueSignalement de bug, demande de fonctionnalité, tâche. Peut être assignée, labelisée, liée à une PR.
LabelsTags colorés pour catégoriser : bug, enhancement, help wanted, good first issue…
MilestonesRegrouper des Issues/PRs par objectif ou version. Pourcentage de complétion automatique.
Fermeture autoMots-clés dans un commit/PR : Fixes #42, Closes #42, Resolves #42 → ferme l'issue au merge.

Forking et contributions open source

Fork workflowFork → clone → branche → modifications → commit → push → PR vers le repo original.
UpstreamLe dépôt original après fork. git remote add upstream <url> pour synchroniser.
CONTRIBUTING.mdGuide de contribution au projet. Conventions de code, process de PR, contact.

GitHub Discussions

Forum de conversation pour un repo ou une organisation. Différent des Issues : pour les questions, annonces, idées. Catégories : General, Q&A, Show and tell, Announcements, Polls.
04

Développement moderne — GitHub Actions

⚙️ Domain 3 · 13%

GitHub Actions — concepts

WorkflowPipeline automatisé défini en YAML dans .github/workflows/. Déclenché par des événements.
Event (déclencheur)push, pull_request, schedule (cron), workflow_dispatch (manuel), release…
JobEnsemble d'étapes (steps) s'exécutant sur un runner. Les jobs s'exécutent en parallèle par défaut (ou en série avec needs).
StepCommande individuelle ou action réutilisable dans un job.
RunnerMachine qui exécute les jobs. GitHub-hosted (ubuntu, windows, macos) ou self-hosted.
ActionBloc réutilisable. GitHub Marketplace : milliers d'actions disponibles. uses: actions/checkout@v4.
💡 Exemple workflow minimal 
on: [push]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm test

CI/CD avec GitHub Actions

CI (Intégration Continue)

  • Tests automatiques à chaque push/PR
  • Linting et analyse statique
  • Build et compilation

CD (Déploiement Continu)

  • Déploiement auto en staging
  • Déploiement en production sur tag
  • Environments & Approvals

GitHub Packages

  • Registre de paquets intégré à GitHub
  • npm, Docker, Maven, NuGet…
  • Accès contrôlé par les permissions repo

GitHub Codespaces & Copilot

CodespacesEnvironnement de développement cloud basé sur VS Code. Configuré via .devcontainer/. Lance en quelques secondes.
GitHub CopilotIA d'assistance au code. Suggestions de code en temps réel, chat, revue de code IA. Abonnement payant (ou inclus pour étudiants/OS).

Sécurité, confidentialité et administration

🔒 Domain 4 · 10%

Protection des branches

Branch Protection RulesRègles sur main : revues obligatoires, checks CI requis, interdire le push direct, interdire le force push.
Ruleset (nouveau)Remplace progressivement les Branch Protection Rules. Plus flexible, s'applique à plusieurs branches via patterns.
CODEOWNERSRevue automatique des propriétaires de code. Placé dans CODEOWNERS, docs/CODEOWNERS ou .github/CODEOWNERS.

Sécurité du code

OutilRôle
DependabotMises à jour automatiques des dépendances vulnérables. Alerts + PRs auto.
Code ScanningAnalyse statique du code (SAST) avec CodeQL. Détecte les vulnérabilités dans le code.
Secret ScanningDétecte les secrets (API keys, tokens) accidentellement commités. Alerte et révoque auto chez certains partenaires.
Security PolicyFichier SECURITY.md : comment signaler des vulnérabilités. Affiché dans l'onglet Security.

Permissions et rôles

RôleAccès
ReadLire le code et créer des Issues
TriageGérer Issues et PRs sans écrire
WritePousser du code, gérer Issues et PRs
MaintainGérer le repo sans accès aux paramètres sensibles
AdminContrôle total, paramètres, accès

Organisations et équipes

OrganisationCompte partagé pour les entreprises/projets. Membres, équipes, repos. Facturation centralisée.
TeamsGroupes de membres avec permissions sur des repos. Mention @org/team dans les commentaires.
EnterprisePlusieurs organisations sous une entreprise. SSO SAML, audit logs, politiques globales.

Bénéfices de la communauté GitHub

Open Source sur GitHub

Licences open sourceMIT (permissive), Apache 2.0 (permissive + brevets), GPL (copyleft), Creative Commons. Fichier LICENSE à la racine.
InnerSourcePratiques open source appliquées en interne dans une entreprise. Collaboration entre équipes avec PRs, Issues, documentation.
StarMarquer un repo comme favori / montrer son appréciation. Pas d'impact fonctionnel, mais indique la popularité.
WatchS'abonner aux notifications d'un repo. Participating, All Activity, Custom ou Ignore.

GitHub Sponsors

Gestion des dépôts

🗂️ Domain 6 · 8%

Types de repos

Public

  • Visible par tout le monde
  • N'importe qui peut forker
  • Gratuit sur github.com

Privé

  • Visible uniquement aux collaborateurs
  • Gratuit (limites features)
  • Advanced Security en option

Internal

  • Visible aux membres de l'organisation
  • Enterprise uniquement
  • InnerSource use case

Fonctionnalités de gestion

TemplatesCréer un repo modèle. Utilisé via "Use this template" → nouveau repo avec les mêmes fichiers.
TopicsTags ajoutés au repo pour le découvrir (ex : react, api). Affichés sur explore.github.com.
ReleasesVersions publiées d'un projet. Tag Git + notes de version + binaires. Basées sur les tags Git.
GitHub PagesHébergement de sites statiques depuis un repo. Branch ou dossier /docs. URL : username.github.io/repo.
WikisDocumentation collaborative attachée au repo. Peut être désactivée. Format Markdown.
ArchivageRepo en lecture seule. Pas de suppression, pas de modification. Conserver le code historique.

ProjectsTableau de bord flexible pour gérer les Issues et PRs. Vues : Table, Board (Kanban), Roadmap (timeline).

Pièges classiques

  • Fork ≠ Clone : Fork = copie sur GitHub (pour contribuer). Clone = copie locale (pour travailler). On clone toujours, même après un fork.
  • Pull ≠ Fetch : git fetch récupère sans fusionner. git pull = fetch + merge. Fetch est plus sûr pour vérifier avant d'intégrer.
  • Merge commit vs Squash vs Rebase : Merge conserve tout l'historique. Squash = un seul commit propre. Rebase = historique linéaire (réécriture). L'examen demande de choisir selon le contexte.
  • Issues ≠ Discussions : Issues = tâches trackées, bugs, features (s'ouvrent et se ferment). Discussions = conversations ouvertes, Q&A, idées (pas fermées).
  • CODEOWNERS n'est pas une protection seule : CODEOWNERS définit les reviewers, mais les Branch Protection Rules doivent exiger les reviews.
  • Dependabot Alerts ≠ Dependabot Updates : Alerts = notifie des vulnérabilités. Updates = crée des PRs pour corriger. Deux fonctionnalités distinctes.
  • git revert ≠ git reset : revert crée un nouveau commit qui inverse les changements (sûr). reset --hard supprime l'historique (dangereux, surtout si partagé).
  • GitHub Actions runners : GitHub-hosted = provisionnés à chaque job (clean). Self-hosted = machine sous votre contrôle (persistante, réseau interne possible).
  • Repo privé ≠ Repo interne : Privé = accès uniquement aux collaborateurs invités. Interne = visible à tous les membres de l'organisation (Enterprise uniquement).
