IAM & Gestion des identités

Règle d'évaluation : Deny explicite > Allow explicite. Par défaut tout est implicitement Deny. SCP + Identity-based policy (intersection). Resource-based policy peut autoriser seule pour ressources cross-account dans la même Organization.

AWS Organizations — Délégation sécurisée

SCP (Service Control Policies)
  • Ne donnent PAS de permissions, limitent les permissions existantes
  • S'appliquent à tous les comptes membres (pas au management account)
  • Deny list (par défaut tout autorisé) ou Allow list
  • Héritage hiérarchique : OU > compte
Delegated Administrator
  • Compte membre gérant un service AWS Organization-wide
  • Ex : SecurityHub, GuardDuty, Config, Macie
  • Le management account reste celui qui délègue
  • Isoler les opérations de sécurité du management account
AWS Control Tower
  • Landing zone multi-comptes avec guardrails
  • Preventive controls = SCP
  • Detective controls = Config Rules
  • Account Factory pour provisionner des comptes

AWS IAM Identity Center (SSO)

  • Permission sets : définissent l'accès dans les comptes cibles
  • Intégration avec Active Directory via AWS Directory Service ou AD Connector
  • SAML 2.0 pour les applications externes
  • SCIM pour le provisionning automatique depuis IdP externe (Okta, Azure AD)
  • Attribute-based access control (ABAC) : tags d'utilisateur → droits dynamiques

Cross-account access

Avec AssumeRole

  • Trust policy sur le rôle cible → autorise le compte source
  • Identity-based policy → sts:AssumeRole sur l'ARN du rôle
  • ExternalId pour les tiers (confusion deputy attack)
  • Durée max : 12h (1h par défaut)

Resource-based policies

  • S3 bucket policy : Principal: {"AWS": "arn:aws:iam::123:root"}
  • KMS Key policy : autoriser les comptes cross-account
  • Pas besoin d'AssumeRole si ressource-based policy seule
  • Plus simple, mais moins de granularité

ABAC avec tags : aws:RequestTag, aws:ResourceTag, aws:PrincipalTag. Idéal pour des policies dynamiques — un utilisateur avec tag Team=Alpha peut accéder aux ressources avec tag Team=Alpha sans modifier les policies.
Domaine 2

Détection des menaces & Monitoring

AWS GuardDuty

Sources de données
  • VPC Flow Logs (automatique)
  • CloudTrail Events (automatique)
  • DNS Logs Route 53 (automatique)
  • S3 Data Events (optionnel)
  • EKS Audit Logs (optionnel)
  • RDS Login Activity (optionnel)
  • Lambda Network Activity (optionnel)
  • Malware Protection (optionnel)
Findings notables
  • UnauthorizedAccess : accès anormal depuis IP suspecte
  • CryptoCurrency : minage de crypto
  • Backdoor : C&C communication
  • Exfiltration : S3ObjectDescribed depuis Tor
  • PrivilegeEscalation : IAM role abuse
  • Recon : port scanning, API enumeration
Architecture multi-comptes
  • Compte administrateur GuardDuty (delegated admin via Organizations)
  • Findings agrégés dans le compte admin
  • EventBridge → Lambda/SNS pour automatisation
  • Suppression rules pour réduire les faux positifs
GuardDuty ≠ SIEM. GuardDuty détecte les menaces basé sur ML et threat intel. Pour SIEM/correlation → Security Hub ou SIEM tiers (Splunk, Sumo Logic) via S3/Kinesis.

AWS Security Hub

  • Agrège les findings de GuardDuty, Inspector, Macie, IAM Analyzer, Firewall Manager, Config
  • ASFF (Amazon Security Finding Format) : format standard pour tous les findings
  • Security standards : CIS AWS Foundations, PCI DSS, AWS Foundational Security Best Practices
  • Custom actions → EventBridge → automatisation
  • Findings Insights : requêtes agrégées sur les findings

AWS CloudTrail

Types d'événements

  • Management events : API calls (par défaut activés)
  • Data events : S3, Lambda (désactivés par défaut, coût)
  • Insights events : détection d'anomalies dans les API calls
  • Network activity events : VPC endpoint calls

Sécurisation des logs

  • S3 bucket avec MFA Delete activé
  • SSE-S3 ou SSE-KMS chiffrement
  • Log File Validation (SHA-256 hash chain)
  • CloudWatch Logs delivery pour alerting en temps réel
  • Trail multi-régions recommandé
CloudTrail Lake : requêtes SQL directes sur les événements (alternative à Athena). Rétention configurable jusqu'à 7 ans. Idéal pour les audits de conformité.

Amazon Macie

  • Découverte automatique de données sensibles (PII, secrets, credentials) dans S3
  • Managed data identifiers (200+) + Custom data identifiers (regex)
  • Findings : SensitiveData, Policy (bucket public, encryption désactivée)
  • Automated sensitive data discovery : scan continu à faible coût
  • Multi-account via Organizations (delegated admin)

AWS Config

  • Enregistrement continu de la configuration des ressources
  • Config Rules : vérification de conformité (managed ou custom Lambda)
  • Conformance Packs : ensemble de règles (CIS, NIST, PCI-DSS)
  • Remediation : SSM Automation pour correction automatique
  • Aggregator : vue multi-comptes et multi-régions
  • Config enregistre les changements ; ne bloque pas (détectif, pas préventif)

Amazon Inspector

EC2 Scanning
  • Agent SSM nécessaire
  • Vulnérabilités OS (CVE)
  • Network reachability (ports exposés)
  • Scan continu automatique
ECR Container Scanning
  • Scan des images à chaque push
  • Enhanced scanning vs Basic scanning
  • Vulnérabilités dans les packages OS et applicatifs
  • Blocage si CRITICAL CVE
Lambda Scanning
  • Dépendances applicatives (node_modules, pip)
  • Code scanning (secrets hardcodés)
  • Scan à chaque déploiement

Sécurité de l'infrastructure

WAF Logging : vers S3, CloudWatch Logs, ou Kinesis Data Firehose. Activer full logging pour investiguer les attaques. Redacted fields pour masquer les données sensibles dans les logs.

AWS Shield

Shield Standard (gratuit)

  • Protection automatique contre les attaques DDoS L3/L4 courantes
  • Inclus pour tous les services AWS
  • Pas de visibilité ni de support dédié

Shield Advanced ($3000/mois)

  • Protection L3/L4/L7 avancée
  • DDoS Response Team (DRT) 24/7
  • Protection cost credits (surge billing)
  • Application Layer DDoS detection & mitigation automatique
  • Real-time visibility via CloudWatch metrics
  • Protège : CloudFront, Route 53, ALB, NLB, EIP, Global Accelerator

AWS Network Firewall

  • Pare-feu stateful/stateless géré au niveau VPC
  • Stateless rules : basées sur 5-tuple (IP, port, protocole)
  • Stateful rules : inspection complète du trafic, Suricata IDS/IPS rules
  • FQDN filtering : filtrage par nom de domaine (TLS inspection)
  • Déployé dans des subnets dédiés (firewall subnets)
  • Architecture : Inspection VPC centralisée via Transit Gateway

AWS Firewall Manager

  • Gestion centralisée des politiques de sécurité sur toute l'Organization
  • Politiques gérées : WAF, Shield Advanced, Security Groups, Network Firewall, Route 53 Resolver DNS Firewall
  • Auto-remediation : applique les policies aux nouveaux comptes/ressources
  • Findings dans Security Hub

VPC Security — Rappels critiques

Security Groups vs NACLs
  • SG : stateful, niveau instance, allow only
  • NACL : stateless, niveau subnet, allow + deny
  • Éphémeral ports (1024-65535) dans NACLs inbound
  • SG reference : un SG peut référencer un autre SG
VPC Flow Logs
  • Capturent les métadonnées des flux réseau
  • Pas le contenu des paquets
  • Destination : CloudWatch Logs, S3, Kinesis
  • Format personnalisable (v5 inclut AWS metadata)
VPC Endpoints
  • Gateway endpoint : S3, DynamoDB (gratuit)
  • Interface endpoint : autres services AWS (PrivateLink)
  • Endpoint policies : restreindre l'accès aux ressources
  • Clé exam : S3 bucket policy avec aws:SourceVpc

AWS Systems Manager (SSM)

  • Session Manager : accès SSH/RDP sans bastion, sans ouverture de ports
  • Parameter Store : stockage sécurisé de paramètres (Standard : gratuit, Advanced : chiffrement KMS)
  • Secrets Manager : rotation automatique des secrets, intégration RDS/Redshift/DocumentDB
  • Patch Manager : automatisation des patchs OS et applications
  • SSM Agent requis sur les instances EC2 (pré-installé sur AMI Amazon Linux 2+)

AWS Certificate Manager (ACM)

  • Provision, gestion et renouvellement automatique des certificats SSL/TLS
  • Publics : Domain Validation (DV), gratuits, pour CloudFront/ALB/API GW
  • Privés : ACM Private CA (autorité de certification privée)
  • ACM Private CA : hiérarchie CA racine/subordonnée, certificats pour services internes
  • Certificats ACM publics : ne peuvent pas être exportés (sécurité)

S3 — Sécurité avancée

Blocage accès public
  • Block Public Access : 4 paramètres (new ACL, existing ACL, new policy, any policy)
  • Au niveau compte et/ou bucket
  • Vérifier avec AWS Config rule : s3-bucket-public-read-prohibited
S3 Object Lock
  • WORM (Write Once Read Many)
  • Governance mode : Admin peut supprimer
  • Compliance mode : Personne ne peut supprimer
  • Legal hold : protection sans expiration
S3 Access Points
  • Simplifient la gestion des accès à grande échelle
  • Chaque access point = endpoint distinct + policy
  • Restriction à un VPC spécifique possible
  • Multi-région : S3 Multi-Region Access Points
Domaine 5

Réponse aux incidents

Workflow de réponse à un incident AWS

  1. Détection : GuardDuty finding → EventBridge rule déclenche l'automatisation
  2. Isolation : Modifier les Security Groups → retirer l'instance du LB → snapshot EBS
  3. Investigation : VPC Flow Logs, CloudTrail, mémoire dump (SSM), logs applicatifs
  4. Éradication : Terminate l'instance compromise, révoquer les credentials IAM
  5. Récupération : Redéployer depuis une AMI saine, rotation des secrets
  6. Post-incident : Mise à jour des détections, rapport de sécurité

Isolation d'une instance compromise

Actions immédiates
  • Attacher un SG restrictif (allow rien en inbound)
  • Détacher des Load Balancers / Auto Scaling Groups
  • Snapshot EBS pour préservation des preuves
  • Activer CloudTrail si pas déjà actif
Investigation mémoire
  • SSM Run Command pour collecter les artefacts
  • EBS snapshot → instance forensics dédiée
  • AMI de l'instance compromise
  • Pas de SSH direct si possible (préserver les preuves)
Credentials compromis
  • Révoquer les sessions IAM actives (aws iam create-access-key + revoke old)
  • Attacher une Deny policy explicite
  • Rotation immédiate via Secrets Manager
  • Vérifier CloudTrail : actions effectuées avant révocation

Automatisation de la réponse

  • EventBridge + Lambda : réponse automatique aux GuardDuty findings
  • AWS Security Hub + Custom Actions : workflow d'investigation personnalisé
  • SSM Automation Runbooks : procédures de remédiation standardisées
  • AWS Step Functions : orchestration de workflows complexes de réponse
  • AWS Systems Manager Incident Manager : gestion des incidents avec runbooks, alerting
AWS Abuse Team : Si vous recevez un email d'AWS Abuse (abuse@amazonaws.com), il faut répondre dans les 24h. Vérifier l'origine de l'activité, isoler les ressources concernées, et confirmer la remédiation.

KMS Key Policy — Structure critique

Règle d'or KMS : Si la Key Policy n'accorde pas l'accès explicitement au compte root, personne ne peut utiliser la clé via IAM policies. La Key Policy est toujours requise — contrairement aux autres ressources AWS.
  • kms:CreateGrant : permettre à d'autres services d'utiliser la clé (EBS, RDS…)
  • kms:Decrypt, kms:GenerateDataKey : opérations de chiffrement/déchiffrement
  • kms:DescribeKey : consulter les métadonnées (souvent oublié)
  • ViaService condition : limiter l'usage d'une clé à un service spécifique

AWS CloudHSM

  • HSM (Hardware Security Module) dédié dans votre VPC
  • Conformité FIPS 140-2 Level 3 (KMS = Level 2 sauf XKS)
  • Vous gérez le HSM — AWS n'a pas accès aux clés
  • Cas d'usage : PKCS#11, JCE, CNG pour applications legacy
  • HSM Cluster : HA avec plusieurs HSM dans différentes AZ
  • Plus cher que KMS, moins d'intégrations natives AWS

Envelope Encryption (chiffrement d'enveloppe)

  1. KMS génère une Data Key (plaintext + encrypted copy)
  2. Chiffrer les données avec la Data Key en plaintext
  3. Stocker uniquement la Data Key chiffrée avec les données
  4. Supprimer la Data Key plaintext de la mémoire
  5. Pour déchiffrer : appeler KMS Decrypt avec la Data Key chiffrée → KMS retourne la plaintext Data Key → déchiffrer les données
Multi-Region Keys : Même key material, différents ARN dans différentes régions. Permet de déchiffrer dans une autre région sans ré-importer les données. Chaque clé reste indépendante.
Domaine 7

Sécurité réseau avancée

AWS Route 53 Resolver DNS Firewall

  • Filtrage des requêtes DNS sortantes depuis le VPC
  • Blocage de domaines malveillants (threat intel lists)
  • Managed domain lists (AWS Managed) ou Custom domain lists
  • Actions : BLOCK (NODATA/NXDOMAIN/Override), ALERT, ALLOW
  • Fail-open vs Fail-closed : comportement si le firewall est indisponible

AWS PrivateLink

  • Expose un service VPC à d'autres VPC sans peering, sans Internet Gateway
  • Endpoint Service côté fournisseur : NLB + VPC Endpoint Service
  • Endpoint côté consommateur : Interface Endpoint (ENI dans le VPC)
  • Trafic reste dans le backbone AWS, pas de chevauchement CIDR

AWS Global Accelerator

  • Réseau Anycast : 2 adresses IP statiques mondiales
  • Traffic entre dans le backbone AWS depuis le PoP le plus proche
  • Protection DDoS via Shield par défaut
  • Failover en 30s entre régions (health checks)
  • Différent de CloudFront : pas de cache, pour TCP/UDP

TLS Inspection avec Network Firewall

  • TLS Inspection Configuration : déchiffre, inspecte, rechiffre le trafic
  • Nécessite ACM Private CA pour signer les certificats
  • Inspection inbound (ingress) et/ou outbound (egress)
  • Performances réduites (overhead déchiffrement)

  • GuardDuty Runtime Monitoring (ECS, EKS, EC2)
  • Inspector Lambda Scanning continu
  • IMDSv2 obligatoire (block IMDSv1)

AWS IAM Access Analyzer

  • Analyse les policies pour identifier l'accès externe non voulu (externe à l'Organization)
  • Types de findings : S3 bucket, IAM Role, KMS Key, Lambda, SQS Queue, Secrets Manager, SNS
  • Policy generation : génère une policy IAM least-privilege basée sur les logs CloudTrail
  • Policy validation : vérifie la syntaxe et les bonnes pratiques d'une policy
  • Zone of trust : account ou Organization

IMDSv2 (Instance Metadata Service)

SSRF protection : IMDSv2 utilise des sessions avec token à durée limitée. Les attaques SSRF qui volaient les credentials EC2 via IMDSv1 (un seul GET suffit) sont bloquées car IMDSv2 nécessite un PUT préalable. Forcer IMDSv2 avec HttpTokens: required dans le Launch Template.

Domaine 10

Sécurité S3 avancée

Presigned URLs vs S3 Access Points

Presigned URLs

  • URL temporaire avec permissions du générateur
  • PUT ou GET, durée max 7 jours (STS tokens: session)
  • Peut être partagé avec des tiers sans compte AWS
  • Révocation difficile (attendre expiration ou révoquer les credentials)

S3 Access Points

  • Endpoints distincts avec policies dédiées
  • Simplifient la gestion pour de nombreux users
  • Peuvent être restreints à un VPC spécifique
  • Révocation immédiate possible

S3 Replication & Sécurité

  • CRR (Cross-Region Replication) : conformité, latence, DR
  • SRR (Same-Region Replication) : agrégation de logs, dev/test depuis prod
  • Réplication : SSE-S3, SSE-KMS (avec grant), SSE-C (non supporté)
  • Delete markers : répliqués optionnellement (attention à la suppression accidentelle)
  • S3 Replication Time Control (RTC) : SLA 15 min garanti, compliance

Pièges classiques à l'examen SCS

Anti-patterns fréquents :
  • Confused Deputy Attack : toujours utiliser ExternalId pour les tiers qui assument vos rôles
  • SCP ne donnent pas de permissions, elles les limitent — un Allow SCP ne suffit pas
  • KMS Key Policy requise — contrairement aux autres ressources, les IAM policies seules ne suffisent pas
  • Bucket ACL vs Bucket Policy : préférer les Bucket Policies (ACL deprecated sauf Object Ownership)
  • IMDSv1 ouvert = vol de credentials EC2 via SSRF → toujours forcer IMDSv2
  • CloudTrail désactivé = pas de visibilité — activer multi-région, protéger avec Log File Validation
  • Detective requiert GuardDuty activé depuis au moins 48h pour les données comportementales
