1Pourquoi Git et à quoi sert le CI/CDFondations
GitVersionnementCI/CDDevOps
Git est un système de gestion de versions : il garde l'historique de chaque fichier, qui a changé quoi, quand et pourquoi, et permet de revenir en arrière ou de travailler à plusieurs sans s'écraser. Analogie : un cahier de bord de chantier où chaque modification est une page datée et signée, avec la possibilité de rouvrir n'importe quelle page ancienne.
Sans GitAvec Git
config_v2_FINAL_ok.ymlUn historique propre, une seule version courante
« Qui a modifié ça ? »git blame, git log
Peur de casser quelque choseRetour arrière en une commande
Travail à deux = écrasementsBranches et fusions
Déploiement manuelPipeline déclenché par un commit (CI/CD)

Le fil du DevOps

  1. Tout est un fichier texte : code, Terraform, playbooks Ansible, manifestes Kubernetes
  2. Tout est dans Git : l'historique devient la mémoire de l'infrastructure
  3. Chaque changement passe par une demande de fusion relue (pull request / merge request)
  4. Un pipeline CI/CD vérifie automatiquement (format, validation, tests, plan) puis déploie
  5. Le résultat est reproductible : on peut reconstruire de zéro
Pour un ex-admin Windows : Git remplace les dossiers « anciennes versions », et un pipeline remplace la liste de clics du « mode opératoire ».

Résoudre un conflit

  1. Git s'arrête et marque les fichiers : git status les liste
  2. Ouvre le fichier : zones <<<<<<<, =======, >>>>>>> (ta version / l'autre)
  3. Garde le bon contenu, supprime les marqueurs
  4. git add fichier puis git commit (ou git merge --continue)
  5. En cas de panique : git merge --abort
  • Branches courtes : une idée, un sujet, quelques jours au plus
  • Mets à jour ta branche avant de fusionner : git fetch puis git merge origin/main (ou rebase)
  • Ne rebase jamais une branche déjà partagée avec d'autres

Le flux de travail courant (GitHub Flow)

  1. git switch -c fix-ntp : une branche par sujet
  2. Modifier, commiter, git push -u origin fix-ntp
  3. Ouvrir une pull request (GitHub) ou merge request (GitLab) vers main
  4. Le pipeline tourne, un collègue relit et commente
  5. Fusion après validation ; suppression de la branche
Réglage conseilléPourquoi
Protéger main (pas de push direct)Tout passe par relecture et pipeline
Exiger des vérifications réussies avant fusionUn pipeline rouge bloque
Au moins 1 approbationUn second regard
Historique linéaire (squash)Un commit propre par fonctionnalité
Même seul, travaille par branche et pull request : tu prends le réflexe, tu gardes un historique lisible, et le pipeline te protège de toi-même.

7Hooks, conventions et bonnes pratiquesGit
pre-commitConventionsTagsRelease
  • Messages de commit : impératif, court en titre (≈ 50 caractères), détail en corps ; des conventions comme Conventional Commits (feat:, fix:, docs:) facilitent les journaux de version
  • Tags : git tag -a v1.2.0 -m "…" pour figer une version ; git push --tags
  • pre-commit : exécuter des vérifications avant chaque commit (format, lint, détection de secrets)
  • CODEOWNERS : désigner les relecteurs obligatoires d'un dossier
  • Monorepo ou plusieurs dépôts : un dépôt « infrastructure » (Terraform, Ansible) distinct des applications est un bon début
# .pre-commit-config.yaml (outil pre-commit) repos: - repo: https://github.com/pre-commit/pre-commit-hooks rev: v5.0.0 # version à vérifier / mettre à jour hooks: - id: check-yaml - id: end-of-file-fixer - id: detect-private-key - repo: https://github.com/antonbabenko/pre-commit-terraform rev: v1.96.0 # idem hooks: - id: terraform_fmt - id: terraform_validate

# .github/workflows/terraform.yml : plan sur pull request, apply manuel sur main name: terraform on: pull_request: paths: [ "terraform/**" ] push: branches: [ main ] jobs: plan: runs-on: ubuntu-latest defaults: { run: { working-directory: terraform } } steps: - uses: actions/checkout@v4 # version à vérifier / mettre à jour - uses: hashicorp/setup-terraform@v3 # idem - run: terraform fmt -check - run: terraform init -backend=false - run: terraform validate - run: terraform plan env: TF_VAR_pve_api_token: ${{ secrets.PVE_API_TOKEN }} # secret du dépôt apply: if: github.ref == 'refs/heads/main' needs: plan environment: production # approbation manuelle exigée runs-on: self-hosted # runner dans ton réseau (Proxmox non exposé) steps: - uses: actions/checkout@v4 - run: terraform -chdir=terraform apply -auto-approve
  • Les secrets viennent du coffre du CI (secrets.X), jamais du dépôt
  • Un Proxmox interne n'est pas joignable depuis les runners hébergés : prévoir un runner auto-hébergé dans ton réseau
  • Épingle les versions des actions (ou leur empreinte) et mets-les à jour : c'est de la chaîne d'approvisionnement

10GitOps et workflow d'équipeGitOps
Argo CDFluxFleetRevue
  • GitOps : le dépôt Git est la source de vérité ; un opérateur (Argo CD, Flux, Fleet) synchronise le cluster sur le dépôt et corrige toute dérive
  • Revue de code : un changement d'infra se relit comme du code (taille raisonnable, terraform plan joint, explication du pourquoi)
  • Environnements : dossiers ou branches par environnement (envs/test, envs/prod), promotion par pull request
  • Retour arrière : git revert du commit fautif, le pipeline redéploie l'état précédent
  • Traçabilité : qui a changé quoi, quand, avec quelle validation (utile pour l'audit)

12Plan de labo et Q/RPratique
Pratique18 questions

Plan de labo en 6 séances

  1. Séance 1 : installer Git, configurer l'identité, créer un dépôt, 5 commits avec add -p, lire log --graph
  2. Séance 2 : .gitignore, détecter un faux secret avec gitleaks, simuler un secret commité et décider quoi faire
  3. Séance 3 : branches, merge, provoquer puis résoudre un conflit, essayer rebase sur une branche perso
  4. Séance 4 : clé SSH, dépôt GitHub / GitLab, branche + pull request relue (par toi-même ou un ami), protection de main
  5. Séance 5 : pipeline de lint (YAML, Terraform fmt / validate) déclenché à chaque pull request
  6. Séance 6 : pipeline plan + apply manuel sur le dépôt du Labo IaC avec un runner dans ton réseau, puis retour arrière par revert

Auto-évaluation — clique pour voir la réponse

Quelle est la différence entre git add et git commit ?

add place les modifications dans l'index (préparation) ; commit enregistre l'index dans l'historique.

À quoi sert git status ?

À voir l'état du dépôt : fichiers modifiés, préparés ou non suivis.

Pourquoi travailler par branches ?

Pour isoler un changement, le relire et le tester avant de le fusionner dans main.

Que contient un fichier .gitignore ?

Les motifs de fichiers que Git ne doit pas suivre (secrets, état Terraform, fichiers temporaires).

Un secret a été commité : que faire en premier ?

Le révoquer ou le changer immédiatement ; nettoyer l'historique ensuite n'est qu'un complément.

Quelle différence entre merge et rebase ?

Merge crée un commit de fusion et garde l'historique réel ; rebase rejoue tes commits sur la base mise à jour pour un historique linéaire (jamais sur une branche partagée).

Comment annuler un commit déjà poussé ?

git revert, qui crée un commit inverse sans réécrire l'historique.

Que fait git reset --hard ?

Déplace la branche et efface les modifications locales : destructif, à éviter sur ce qui est partagé.

À quoi sert git reflog ?

À retrouver un commit « perdu » grâce au journal des déplacements de HEAD.

Qu'est-ce qu'une pull request ?

Une demande de fusion d'une branche, avec relecture et pipeline, avant intégration dans main.

Quelle différence entre CI et CD ?

CI : vérifier et tester automatiquement chaque changement ; CD : le livrer automatiquement (ou après validation) vers un environnement.

Qu'est-ce qu'un runner ?

La machine qui exécute les jobs du pipeline ; auto-hébergé s'il doit joindre un réseau interne.

Où mettre les secrets d'un pipeline ?

Dans le coffre du CI (secrets / variables protégées), jamais dans le dépôt.

Pourquoi un terraform plan sur chaque pull request ?

Pour relire exactement ce qui va changer avant d'accepter la fusion.

Pourquoi une approbation avant terraform apply en production ?

Pour éviter un déploiement involontaire : un humain valide le plan.

Qu'est-ce que le GitOps ?

L'état voulu est dans Git et un opérateur synchronise le cluster, détecte la dérive et permet le retour arrière par Git.

Que signifie « détached HEAD » ?

On est positionné sur un commit et non sur une branche : créer une branche pour garder son travail.

Que faire si git push est rejeté (non-fast-forward) ?

Récupérer les commits distants (pull ou fetch + merge / rebase), puis repousser.
