1Pourquoi automatiser Proxmox (vue d'ensemble DevOps)Les outils
IaCPackerTerraformAnsible
Idée : décrire l'infrastructure dans des fichiers versionnés (Git) plutôt que de cliquer. On passe de « je crée une VM » à « je déclare ce que je veux, l'outil s'occupe du reste, et je peux le refaire à l'identique ». Les versions d'outils changent vite : les exemples sont à valider avec terraform validate / ansible-lint sur ta version.

Qui fait quoi

OutilRôlePour Proxmox
PackerFabrique des images / modèles reproductiblesConstruit un modèle de VM (ISO → modèle) via les builders proxmox-iso et proxmox-clone
TerraformCrée et supprime l'infrastructure (déclaratif, état)VM, conteneurs, stockages, pools, réseaux, utilisateurs via un provider qui parle à l'API
AnsibleConfigure ce qui existe (idempotent, sans agent)Configure les hôtes Proxmox et les invités ; modules Proxmox pour piloter l'API
cloud-initPersonnalise une VM au premier démarrageClé SSH, utilisateur, IP, nom : injectés par Proxmox dans un disque dédié
Git + CIHistorique, revue, déploiement contrôléPipeline : validation, plan, approbation, application
API / pveshLe socle de tout le resteTout outil passe par l'API REST de Proxmox (port 8006)

Le flux type

Packer -> modèle « tpl-ubuntu » (cloud-init) Terraform -> clone N VM depuis le modèle (IP, CPU, RAM, disque) Ansible -> configure les VM (paquets, services, sécurité) Git + CI -> tout est versionné, relu, appliqué par pipeline

Équivalences pour un profil Windows / Hyper-V

HabitudeÉquivalent ici
PowerShell + module Hyper-Vpvesh, qm, API REST ; PowerShell peut aussi appeler l'API avec Invoke-RestMethod

Modèles Hyper-V / sysprepModèle Proxmox + cloud-init (Linux) ; Windows : sysprep + Packer
SCVMM / WACInterface web, plus l'API pour tout ce qui se répète
Poste de travail Windows : Ansible ne tourne pas nativement comme contrôleur sous Windows : utiliser WSL2 (Linux) pour Ansible. Terraform et Packer existent en binaire Windows.
2L'API Proxmox, pvesh et appels directsAPI
RESTpveshcurlPowerShell
Fait central : l'interface web, qm, pvesh, Terraform et Ansible utilisent la même API REST : https://HÔTE:8006/api2/json/…. Le visualiseur d'API de la documentation (API Viewer) liste chaque chemin, méthode et paramètre.

Authentification : ticket ou jeton

MéthodeUsageRemarque
Ticket + CSRFSession interactive (mot de passe, TOTP)Expire (2 h) ; le jeton CSRF est requis pour les écritures
Jeton d'APIAutomatisation (CI, Terraform, Ansible)Pas de mot de passe ; en-tête Authorization: PVEAPIToken=USER@REALM!JETON=SECRET
# Lister les VM avec un jeton (curl) curl -s -k -H "Authorization: PVEAPIToken=terraform@pve!tf=$PVE_TOKEN_SECRET" \ "https://pve1.lab.local:8006/api2/json/cluster/resources?type=vm" # Même chose en local sur un nœud, sans jeton (pvesh utilise l'identité de l'utilisateur) pvesh get /cluster/resources --type vm --output-format json # Cloner un modèle (écriture) pvesh create /nodes/pve1/qemu/9000/clone --newid 201 --name web-01 --full 1 # Équivalent PowerShell 7 $h = @{ Authorization = "PVEAPIToken=terraform@pve!tf=$env:PVE_TOKEN_SECRET" } Invoke-RestMethod -Uri "https://pve1.lab.local:8006/api2/json/cluster/resources?type=vm" -Headers $h -SkipCertificateCheck
  • -k / -SkipCertificateCheck ignorent la vérification TLS : acceptable en labo seulement ; en production, installer un certificat de confiance ou la CA interne (pvenode cert, ACME)
  • Les réponses sont en JSON dans la clé data ; les opérations longues renvoient un UPID (identifiant de tâche) à suivre
  • Toutes les opérations asynchrones (clone, démarrage, sauvegarde) sont des tâches : l'outil doit attendre qu'elles se terminent
3Comptes de service, rôles et jetons (moindre privilège)Sécurité
pveumJetonRôleprivsep
Règle : un outil d'automatisation n'utilise jamais root@pam. On crée un utilisateur de service, un rôle limité, un jeton par outil, et on affecte les droits sur le bon chemin (/, /vms, /pool/NOM…).
# 1. Un rôle limité à l'approvisionnement de VM pveum role add Provisioner --privs "VM.Allocate,VM.Clone,VM.Audit,VM.PowerMgmt,VM.Config.CPU,VM.Config.Memory,VM.Config.Disk,VM.Config.Network,VM.Config.Options,VM.Config.Cloudinit,VM.Config.CDROM,VM.Config.HWType,VM.GuestAgent.Audit,Datastore.Audit,Datastore.AllocateSpace,Sys.Audit,SDN.Use,Pool.Audit" # 2. Un utilisateur de service dans le realm « pve » pveum user add terraform@pve --comment "Automatisation" pveum aclmod / --users terraform@pve --roles Provisioner # 3. Un jeton AVEC séparation de privilèges (le secret n'est affiché qu'une fois) pveum user token add terraform@pve tf --privsep 1 pveum aclmod / --tokens 'terraform@pve!tf' --roles Provisioner # Vérifier pveum user token permissions terraform@pve tf
  • Séparation de privilèges (privsep 1) : le jeton n'a que ses propres ACL, dans la limite de ceux de l'utilisateur ; les deux doivent recevoir le rôle
  • Sans séparation, le jeton hérite de tous les droits de l'utilisateur
  • Le secret ne s'affiche qu'une fois : le stocker immédiatement dans un coffre (Vault, gestionnaire de secrets de la CI, variable chiffrée)
  • Un jeton par outil et par environnement ; durée de vie (--expire) et rotation planifiées
  • Proxmox 9 : le privilège VM.Monitor a été supprimé (remplacé par Sys.Audit et des droits fins) ; un ancien rôle copié de la version 8 peut échouer
Certaines opérations restent réservées à root@pam (conteneur privilégié avec options spéciales, passthrough PCI/USB sans mapping de ressources, certains paramètres de migration). Elles ne passent pas avec un jeton ordinaire : prévoir une voie dédiée plutôt que de donner root à tout le monde.
4Cloud-init et modèles de VM : la base de toutModèle
qmcloud-initTemplate
Un modèle cloud-init est l'équivalent d'une image « dorée » : on le clone, et chaque clone reçoit son nom, son IP et sa clé SSH au premier démarrage. C'est la brique commune de Terraform, d'Ansible et de la migration.
# Construire un modèle à partir d'une image cloud (séquence de la documentation) wget https://cloud-images.ubuntu.com/…/…-server-cloudimg-amd64.img qm create 9000 --name tpl-ubuntu --memory 2048 --net0 virtio,bridge=vmbr0 --scsihw virtio-scsi-pci qm set 9000 --scsi0 local-lvm:0,import-from=/chemin/…-cloudimg-amd64.img qm set 9000 --ide2 local-lvm:cloudinit qm set 9000 --boot order=scsi0 qm set 9000 --serial0 socket --vga serial0 qm set 9000 --agent enabled=1 qm template 9000 # Cloner et personnaliser qm clone 9000 201 --name web-01 --full 1 qm set 201 --ciuser ops --sshkeys ~/.ssh/id_ed25519.pub --ipconfig0 ip=192.168.10.51/24,gw=192.168.10.1 --nameserver 192.168.10.2 qm resize 201 scsi0 +20G qm start 201
Option cloud-initRôle
ciuser · cipasswordUtilisateur par défaut (préférer les clés SSH au mot de passe)
sshkeysClé(s) publique(s) SSH du compte
ipconfig0 (…n)Réseau de la carte net0 : ip=…/24,gw=… ou ip=dhcp
nameserver · searchdomainDNS de la VM (sinon ceux de l'hôte)
cicustomFichiers utilisateur / réseau / vendor (snippets) pour aller plus loin
  • Si on modifie la config cloud-init après le premier démarrage, il faut régénérer l'image cloud-init (qm cloudinit update 201) puis redémarrer ; l'OS ne rejoue pas toujours tout seul
  • Installer qemu-guest-agent dans le modèle (via cicustom ou en personnalisant l'image) : indispensable pour que les outils lisent l'IP de la VM
  • Un modèle se clone en lien (rapide, dépend du modèle) ou en clone complet (indépendant) selon le stockage
  • Windows : pas de cloud-init natif de la même façon ; utiliser sysprep + Packer pour les modèles
5Packer : fabriquer des modèles reproductiblesPacker
proxmox-isoproxmox-cloneHCL
Packer automatise la création du modèle : il démarre une VM sur Proxmox, l'installe ou la prépare, puis la convertit en modèle. Deux builders : proxmox-iso (depuis une ISO) et proxmox-clone (depuis un modèle existant).
packer { required_plugins { proxmox = { version = "~> 1" source = "github.com/hashicorp/proxmox" } } } # Squelette : à compléter avec les options exactes de la doc du plugin source "proxmox-clone" "ubuntu" { proxmox_url = var.pve_url # https://pve1:8006/api2/json username = var.pve_token_id # terraform@pve!packer token = var.pve_token_secret # jamais en clair dans le dépôt insecure_skip_tls_verify = false node = "pve1" clone_vm = "tpl-ubuntu-base" vm_name = "tpl-ubuntu-golden" ssh_username = "ops" } build { sources = ["source.proxmox-clone.ubuntu"] provisioner "shell" { inline = ["sudo apt-get update", "sudo apt-get -y install qemu-guest-agent"] } }
  • packer init télécharge le plugin, packer validate vérifie, packer build construit
  • Intérêt : modèles à jour et identiques (correctifs, agent, durcissement) reconstruits régulièrement par la CI
  • Les noms exacts des options (proxmox_url, token, clone_vm…) sont à vérifier dans la page du plugin avant usage
6Terraform avec Proxmox (provider bpg/proxmox)Terraform
ProviderVMÉtatVariables
Les exemples ci-dessous utilisent le provider bpg/proxmox (version ~> 0.122 au moment de la lecture de la doc). D'autres providers existent : vérifier l'activité et la compatibilité PVE 9 avant de choisir pour un projet réel.

Configuration du provider et authentification

terraform { required_providers { proxmox = { source = "bpg/proxmox" version = "~> 0.122.0" } } } variable "pve_endpoint" { type = string } variable "pve_api_token" { type = string, sensitive = true } # terraform@pve!tf=SECRET provider "proxmox" { endpoint = var.pve_endpoint # https://pve1.lab.local:8006/ api_token = var.pve_api_token insecure = false # true seulement en labo (certificat auto-signé) ssh { agent = true username = "terraform" # requis pour certaines ressources (snippets, import disque par fichier) } }
Mode d'authentificationUsage
Jeton d'API (api_token / PROXMOX_VE_API_TOKEN)Recommandé pour la production et la CI
Ticket (auth_ticket + csrf_prevention_token)Scripts, avec TOTP
Utilisateur / mot de passeDéveloppement, tests
  • SSH n'est requis que pour : envoi de snippets / certains fichiers, import de disque par source_file.path, entrées idmap de conteneurs. Créer / modifier / supprimer VM et conteneurs, stockages, pools, utilisateurs : API seule
  • Avec un jeton, le mot de passe SSH n'est pas hérité : charger une clé dans ssh-agent ou la déclarer dans le bloc ssh ; l'utilisateur SSH non root doit avoir sudo sans mot de passe sur les commandes nécessaires (règles strictes, pas de sudo libre sur qm ni de joker *)
  • TLS 1.3 est exigé par défaut sur l'API (min_tls pour assouplir)
  • Avec un jeton, garder SDN.Audit ou SDN.Use dans le rôle, sinon les ponts sont invisibles et le provider échoue (« interface not found »)

Créer des VM par clonage du modèle

resource "proxmox_virtual_environment_vm" "web" { for_each = toset(["web-01", "web-02"]) name = each.key node_name = "pve1" tags = ["terraform", "web"] clone { vm_id = 9000 # le modèle cloud-init } agent { enabled = true } cpu { cores = 2 type = "x86-64-v2-AES" } memory { dedicated = 2048 } disk { datastore_id = "local-lvm" interface = "scsi0" size = 20 discard = "on" iothread = true } network_device { bridge = "vmbr0" } initialization { ip_config { ipv4 { address = "dhcp" } } user_account { username = "ops" keys = [var.ssh_public_key] } } }
À valider : les noms de blocs viennent de ma connaissance du provider ; la page de la ressource proxmox_virtual_environment_vm fait foi. Lance toujours terraform validate puis terraform plan en labo.

Le cycle de travail

terraform init # télécharge le provider terraform fmt -recursive terraform validate terraform plan -out tfplan # lit l'API, montre ce qui changera terraform apply tfplan # applique exactement ce plan terraform destroy # supprime ce que Terraform gère (labo) terraform import <adresse> <id> # rattacher une VM déjà existante terraform state list

Bonnes pratiques Terraform

  • État (terraform.tfstate) : il contient des données sensibles ; ne jamais le commiter. Utiliser un backend distant avec verrouillage et sauvegarde
  • .gitignore : *.tfstate*, .terraform/, *.tfvars contenant des secrets, tfplan
  • Secrets via variables d'environnement (TF_VAR_…, PROXMOX_VE_API_TOKEN) ou coffre-fort ; marquer les variables sensitive = true
  • for_each plutôt que count pour des VM nommées (retirer un élément ne décale pas les autres)
  • lifecycle { prevent_destroy = true } sur les ressources critiques ; ignore_changes pour ce qu'Ansible ou l'exploitation modifie
  • Fixer les versions du provider (~>) et commiter .terraform.lock.hcl
  • Les modifications manuelles dans l'interface créent une dérive : plan la détecte
7Ansible avec Proxmox (collection community.proxmox)Ansible
ModulesInventaire dynamiquePlaybooksHôtes
Deux usages distincts : (1) piloter l'API avec les modules Proxmox (créer / cloner / démarrer des VM) ; (2) configurer des machines (les hôtes Proxmox eux-mêmes, ou les invités) en SSH comme n'importe quel Linux. Les modules Proxmox sont dans la collection community.proxmox.
# Installation (contrôleur Linux ou WSL2) ansible-galaxy collection install community.proxmox pip install proxmoxer requests # prérequis des modules API sur le contrôleur

Modules principaux

ModuleRôle
community.proxmox.proxmox_kvmCréer, cloner, démarrer, arrêter, supprimer des VM (QEMU/KVM) ; options cloud-init (ciuser, sshkeys, ipconfig, nameservers)
community.proxmox.proxmoxConteneurs LXC
proxmox_disk · proxmox_nicDisques et cartes réseau d'une VM
proxmox_templateModèles de conteneurs / ISO sur un stockage
proxmox_backupLancer une sauvegarde
proxmox_vm_info · proxmox_user · proxmox_user_infoLecture d'informations et gestion des utilisateurs

Exemple : cloner un modèle et démarrer

- name: Déployer web-01 depuis le modèle hosts: localhost gather_facts: false tasks: - name: Cloner community.proxmox.proxmox_kvm: api_host: pve1.lab.local api_user: ansible@pve api_token_id: ansible api_token_secret: "{{ pve_token_secret }}" # depuis Ansible Vault / variable d'environnement validate_certs: true node: pve1 clone: tpl-ubuntu name: web-01 newid: 201 storage: local-lvm full: true timeout: 300 - name: Démarrer community.proxmox.proxmox_kvm: api_host: pve1.lab.local api_user: ansible@pve api_token_id: ansible api_token_secret: "{{ pve_token_secret }}" name: web-01 node: pve1 state: started
  • state : present, started, stopped, restarted, absent, template…
  • Par sécurité, la mise à jour de net, virtio, ide, sata, scsi est désactivée par défaut (un changement de réseau régénère la MAC, un disque virtio crée un nouveau disque) : update_unsafe: true pour l'autoriser
  • Les modules ne suppriment ni ne recréent rien « magiquement » : lire la doc du module avant de s'en servir pour modifier une VM existante

Inventaire dynamique : les VM Proxmox deviennent des hôtes Ansible

# lab.proxmox.yml (le nom doit se terminer par .proxmox.yml) plugin: community.proxmox.proxmox url: https://pve1.lab.local:8006 user: ansible@pve token_id: ansible token_secret: "{{ lookup('env', 'PVE_TOKEN_SECRET') }}" validate_certs: true want_facts: true # Test ansible-inventory -i lab.proxmox.yml --graph

Configurer les hôtes Proxmox eux-mêmes

- hosts: pve_nodes become: true tasks: - name: Fuseau horaire et NTP ansible.builtin.apt: name: chrony state: present - name: Utilisateur de service pour l'API (idempotent) ansible.builtin.command: pveum user list changed_when: false - name: Déposer le fichier sysctl (plus /etc/sysctl.conf sous PVE 9) ansible.builtin.copy: dest: /etc/sysctl.d/90-lab.conf content: "net.ipv4.ip_forward = 1\n" mode: "0644"
Idempotence : une tâche rejouée ne doit rien changer. Pour command/shell, utiliser changed_when, creates ou un test préalable.
8Terraform + Ansible ensemble, et GitOpsIntégration
PipelineSecretsCIRolling update

Répartition des rôles

Terraform : le « quoi existe »

  • VM, disques, réseaux, pools, droits
  • Sortie (output) des IP / noms
  • État partagé et verrouillé

Ansible : le « comment c'est configuré »

  • Paquets, services, utilisateurs, durcissement
  • Mises à jour des hôtes Proxmox
  • Inventaire dynamique depuis l'API

cloud-init : le pont

  • Amorce SSH + IP à la création
  • Permet à Ansible de se connecter dès le premier démarrage

Organisation du dépôt Git

infra/ packer/ # modèles terraform/ envs/lab/ envs/prod/ modules/vm/ # module réutilisable « une VM Linux » ansible/ inventories/ roles/ playbooks/ .gitignore README.md .github/workflows/ (ou .gitlab-ci.yml)

Pipeline type

  1. Pull request : fmt, validate, ansible-lint, terraform plan posté en commentaire
  2. Relecture par un pair, puis fusion
  3. Application : terraform apply avec approbation manuelle pour la production, puis ansible-playbook
  4. Contrôle de dérive planifié : un plan nocturne qui alerte s'il n'est pas vide
Le runner doit atteindre l'API Proxmox (réseau interne, port 8006). Utiliser un runner auto-hébergé dans le réseau d'administration plutôt que d'exposer l'API sur Internet.

Mise à jour des nœuds en continu (rolling update)

- hosts: pve_nodes serial: 1 # un nœud à la fois : le cluster garde son quorum become: true tasks: - name: Évacuer les VM du nœud (migration / mode maintenance HA selon la version) ansible.builtin.debug: msg="à adapter : ha-manager / qm migrate" - name: Mettre à jour ansible.builtin.apt: update_cache: true upgrade: dist - name: Redémarrer si le noyau a changé ansible.builtin.reboot: reboot_timeout: 900 - name: Attendre le quorum ansible.builtin.command: pvecm status register: q until: "'Quorate' in q.stdout" retries: 20 delay: 15 changed_when: false
  • serial: 1 est la clé : jamais deux nœuds en même temps sur un cluster à 3
  • Vérifier pvecm status (drapeau Quorate) avant de passer au nœud suivant
  • Pour une montée de version majeure (8 → 9), utiliser la procédure officielle et pve8to9 ; l'automatiser seulement après l'avoir réussie à la main en labo

10Automatiser la migration VMware → ProxmoxMigration
TerraformAnsibleqm importovfPost-migration
L'import d'une VM VMware reste une opération à surveiller (voir la fiche Proxmox VE, section 16). L'automatisation sert surtout à préparer la cible, traiter les lots et standardiser l'après-migration.
ÉtapeOutilIdée
Inventaire de la sourceScript (PowerCLI) / export CSVAlimenter l'inventaire des VM (voir le runbook interactif)
Préparer la cibleTerraformCréer pools, stockages, étiquettes, droits, ponts / VLAN avant les vagues
ImporterAssistant ESXi, ou qm importovf / qm disk import en scriptUn script par lot ; sérialiser (pas plus de quelques disques en parallèle)
Après importAnsibleInstaller qemu-guest-agent, pilotes VirtIO (Windows), réglages réseau, retrait de VMware Tools
ContrôleAnsible / pveshRapport : agent actif, sauvegarde faite, étiquette de vague, VM source éteinte
Sauvegarde et HATerraform / jobsInscrire la VM aux sauvegardes et à la HA selon sa criticité
# Lot d'import (squelette) : une VM à la fois for ovf in /srv/export/*/*.ovf; do vmid=$(pvesh get /cluster/nextid) qm importovf "$vmid" "$ovf" local-lvm --format qcow2 || { echo "ECHEC $ovf"; continue; } qm set "$vmid" --cpu x86-64-v2-AES --scsihw virtio-scsi-single --agent enabled=1 echo "$ovf -> VM $vmid" done
Un script d'import ne remplace pas le PoC : tester d'abord sur une VM jetable, garder la VM source éteinte, ne jamais démarrer la même VM des deux côtés.

Pourquoi utiliser un jeton d'API plutôt que le mot de passe root ?

Pas de mot de passe à diffuser, droits limités par rôle et par chemin, révocable individuellement, adapté à la CI.

Que fait l'option privsep sur un jeton ?

Le jeton ne reçoit que ses propres ACL (dans la limite de celles de l'utilisateur) ; sans elle, il hérite de tous les droits de l'utilisateur.

Quand le secret d'un jeton est-il visible ?

Une seule fois, à la création : il faut le stocker aussitôt dans un coffre.

Quelle est la différence entre Terraform et Ansible ?

Terraform crée et supprime l'infrastructure de façon déclarative avec un état ; Ansible configure ce qui existe, de façon idempotente et sans agent.

À quoi sert Packer ?

À fabriquer des modèles de VM reproductibles (builders proxmox-iso et proxmox-clone).

Pourquoi un modèle cloud-init ?

Chaque clone reçoit au premier démarrage son nom, son IP et sa clé SSH ; c'est la brique commune de Terraform, Ansible et de la migration.

Que faire si on change la config cloud-init après le premier démarrage ?

Régénérer l'image cloud-init (qm cloudinit update) puis redémarrer la VM.

Quand le provider Terraform a-t-il besoin de SSH ?

Pour l'envoi de snippets et de certains fichiers, l'import de disque par source_file.path et les entrées idmap des conteneurs ; le reste passe par l'API.

Pourquoi ne pas commiter terraform.tfstate ?

Il contient des données sensibles et l'état réel ; il faut un backend distant avec verrouillage et sauvegarde.

Pourquoi for_each plutôt que count pour des VM nommées ?

Retirer un élément ne décale pas les autres ressources, contrairement à un index numérique.

Qu'est-ce que la dérive et comment la détecter ?

Un écart entre le code et la réalité (modification manuelle) ; un terraform plan régulier la montre.

Comment Ansible découvre-t-il les VM Proxmox ?

Avec le plugin d'inventaire community.proxmox.proxmox (fichier se terminant par .proxmox.yml) qui lit l'API.

Quel prérequis Python pour les modules API Ansible ?

proxmoxer et requests sur le contrôleur.

Pourquoi serial: 1 dans un playbook de mise à jour ?

Pour traiter un nœud à la fois et préserver le quorum du cluster.

Pourquoi un runner de CI auto-hébergé ?

Pour atteindre l'API Proxmox sur le réseau d'administration sans l'exposer sur Internet.

Quel privilège a disparu en Proxmox VE 9 qui peut casser un ancien rôle ?

VM.Monitor, remplacé par Sys.Audit et des droits plus fins.

Comment automatiser l'après-migration VMware ?

Un playbook Ansible : agent invité, pilotes VirtIO, réseau, retrait de VMware Tools, puis rapport de contrôle.

Pourquoi sérialiser les imports en lot ?

Les imports sollicitent l'ESXi (connexions, bande passante) et le stockage ; trop de parallélisme provoque erreurs et lenteurs.
